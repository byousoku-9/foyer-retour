# foyer-retour

Un retour à trois problématiques partagées par l'équipe IA de Foyer — un chatbot pour les nouveaux arrivants au Luxembourg, un sinistre confronté aux conditions générales d'une assurance habitation, un « RAG » sur un Excel de cent mille lignes — prouvé par deux prototypes déployés et une réponse d'architecture pour le troisième.

Le fil rouge : **on ne gagne pas sur « comment on retrouve », on gagne sur « comment on prouve ».** Chaque affirmation montrée à l'utilisateur a survécu à une vérification par du code ; ce que le système ne sait pas est dit, avec la preuve.

## État

Dépôt en construction (août 2026). Story 1.0 livrée : contrats typés du domaine, configuration, `normalize()`, outillage de tests sans réseau, copie du site, infrastructure GCP amorcée. Story 1.1 : le guide est ingéré en arbre de blocs (`data/lux-guide/`), chargé en lecture seule et indexé (`sommaire`, `ouvrir_noeud`, `chercher`) ; son sommaire compact est versionné. Story 1.2 : le contrat AXA OptiHome 2017 est téléchargé (hash vérifié), découpé en blocs par page avec lignes et boîtes (`data/axa-lu-optihome-2017/`), et ses quatre clauses du cas « bougie » sont typées par overlay manuel. Story 1.3 : le client Claude unique (`server/app/llm/`) — tiers, prix, budget par requête, prompts versionnés, erreurs typées. Story 1.4 : les trois premières étapes (`server/app/steps/`) — *comprendre*, *retrouver* (déterministe, sans modèle) et *rédiger* — produisent une ébauche dont chaque affirmation cite un bloc du corpus. Story 1.5 : *vérifier* confronte chaque citation au corpus (code pur) puis juge la pertinence en un seul appel groupé, *restituer* rend la réponse depuis les seules affirmations qui ont survécu, et `server/app/pipelines/guide.py` enchaîne les cinq étapes — court-circuits, relance unique, trace complète. Story 1.6 : le serveur répond sur HTTP (`server/app/api/`) — `POST /api/v1/chat`, `GET /api/v1/sante`, les alias historiques `/chat` et `/sante`, la copie du site sous `/guide/`, un accueil provisoire sur `/` et une page d'attente sur `/sinistre/`, le tout sur **une seule origine** (donc pas de CORS), avec identifiant de requête, journal JSON sans texte, limiteur best-effort et bornes d'entrée. Story 1.7 : l'onglet Assistant de la copie du site parle au serveur qui la sert, affiche ses citations sous chaque phrase et n'a plus aucun repli silencieux. Story 1.8 : un sinistre décrit obtient un verdict conservateur « au regard des conditions générales seules » — la table d'AD-6 est du code pur (`server/app/domain/verdict.py`), *vérifier* dérive l'applicabilité de chaque clause depuis des valeurs typées demandées dans le **même** appel groupé, et `server/app/pipelines/sinistre.py` rejoue la chaîne des cinq étapes sur le contrat AXA. Story 1.9 : ce pipeline est **servi** — `GET /api/v1/documents`, `GET /api/v1/documents/{doc_id}/report`, `POST /api/v1/sinistre` — et `/sinistre/` n'est plus une page d'attente : on y décrit un sinistre et on y lit le verdict, sa portée, les faits compris, le paquet manquant, les questions à poser et les clauses citées avec leur type, leur page et leurs statuts. Story 1.10 : le système **se mesure** — `server/evals/run.py` exécute les questions-témoins par le pipeline réel et écrit `manifest.gate` (`--gate {doc_id} --profile vertical`), les deux documents portent un gate `vertical` adossé à un cas témoin chacun (relu par la boucle ; la contresignature humaine reste due, et `/` le dit), `ALLOW_UNGATED` quitte l'image de production, et l'accueil sur `/` annonce le niveau de validation **lu sur `/api/v1/sante`** — avec la réponse écrite au sujet 3. Story 1.11 : le dépôt se déploie tout seul — un push sur `main` construit l'image par Cloud Build, met la révision en ligne **sans trafic** sous un tag, joue quatre smoke tests sur elle (`sante`, les trois pages, et les deux cas témoins du gate rejoués par HTTP), et ne promeut le trafic que s'ils passent tous ; les pull requests, elles, passent par le lint et la suite hors ligne sans rien déployer. Les stories 2.1 à 2.3 ont ensuite ajouté le dictionnaire enrichi, la continuité conversationnelle et l'exploitation bornée du profil. Story 2.4 : le guide répond désormais en français, anglais, allemand ou portugais ; la langue est décidée une fois, les phrases composées par le code sont traduites, les citations restent en français mot pour mot, et le front rend visibles traduction et repli de détection. Story 2.5 ajoute « Pourquoi cette réponse » et le mode dégradé honnête. La story 2.6 ajoute la variante `outils`, autre implémentation de la seule étape *retrouver* : la chaîne, le préfixe et les schémas de *rédiger* restent communs ; seul son plafond de sortie passe à 1 792 tokens sur le chemin outils afin de tenir sous 0,10 €. Voir « Déploiement » et `docs/tests-live.md` pour les preuves détaillées de chaque livraison.

## Lancer

```bash
uv sync                                   # Python 3.13 et dépendances épinglées (pyproject.toml, uv.lock)
cp .env.example .env                      # puis renseigner ANTHROPIC_API_KEY (jamais commité)
uv run python -m server.app.llm.models --check   # vérifie que les IDs de modèles existent (exit 2 sans clé)
uv run uvicorn server.app.api.main:app --port 8787 --proxy-headers --forwarded-allow-ips='*'
```

Puis <http://localhost:8787/> : l'accueil (les trois entrées, la réponse au sujet 3, le niveau de validation lu sur l'API), le guide sous `/guide/`, l'outil sinistre sous `/sinistre/`, l'API sous `/api/v1/`.

```bash
curl -s localhost:8787/api/v1/sante | python3 -m json.tool
curl -s -X POST localhost:8787/api/v1/chat -H 'X-Forwarded-For: 203.0.113.7' \
     -H 'content-type: application/json' \
     -d '{"question":"Quel délai pour déclarer mon arrivée ?","profil":{},"historique":[]}'
```

`--proxy-headers --forwarded-allow-ips='*'` dit à uvicorn de croire le proxy sur le schéma et l'adresse d'origine : c'est ce qui garde les redirections de `/guide` en `https` derrière Cloud Run. Le limiteur, lui, n'en dépend pas — il lit l'en-tête `X-Forwarded-For` directement, comme AD-13 le demande. En `ENV=dev` l'en-tête est facultatif (identité `local`) ; en production, une requête de pipeline qui n'en porte pas est refusée en 400.

Aucun réseau.
- `tests/test_langues_live.py` rejoue six questions réelles (deux EN, deux DE, deux PT) et leur contrôle `micro` par retraduction ; les fixtures gardent ce contrôle hors réseau dans la suite ordinaire.

- Les seuils numériques vivent dans `server/app/config.py` et se surchargent par variable d'environnement.
- Ré-enregistrer une fixture LLM : supprimer `tests/llm_fixtures/{module}.{test}.json` puis relancer ce test avec `ANTHROPIC_API_KEY` renseignée (réseau, coût) ; committer le JSON avec le pourquoi.

La règle se tient **avant** le commit, jamais après (reprise différée 1.11).

## Questions-témoins et gate de service

Le golden set vit dans `server/evals/cases/{guide,sinistre}/*.yaml`, au schéma d'AD-14 (`id`, `suite`, `profile`, `question`, `expected`, `truth`, `mode_attendu`). Le runner de la story 1.10 est **minimal et borné** : il exécute un cas par le pipeline réel, lui donne un `label` du vocabulaire fixe d'AD-14, et refuse explicitement ce qu'il ne sait pas faire plutôt que de le simuler.

```bash
# Les évals refusent de tourner sans clé (AD-14) : les unitaires passent sans, les évals non.
uv run python -m server.evals.run --suite guide          # exécute la suite, un cas par ligne
uv run python -m server.evals.run --case s-bougie-canape # un seul cas
uv run python -m server.evals.run --gate lux-guide --profile vertical              # écrit le gate
uv run python -m server.evals.run --gate axa-lu-optihome-2017 --profile vertical
```

Codes de sortie, et ce qu'ils font au manifest :

| code | situation | `data/manifest.json` |
|---|---|---|
| 0 | tous les cas `ok` | gate écrit `evals_ok: true` (avec `--gate`) |
| 1 | un cas rend un mauvais label, ou laisse une attente inassouvie | **avec `--gate`** : gate écrit `evals_ok: false`, le document part en `gate_echoue` au prochain démarrage. Sans `--gate` : rien n'est écrit |
| 2 | refus : pas de clé, profil ou suite non livrés, cas invalide, document non servi | **non modifié** |
| 3 | incident : `Timeout`, `LlmUnavailable`, `BudgetExceeded`, plafond de run atteint | **non modifié** |

La ligne de partage entre 1 et 3 est celle d'AD-8 : un mauvais label est un **résultat**, et le gate est fait pour le consigner ; un incident réseau ne dit rien du système mesuré, et le laisser retirer un document du service serait une panne inventée.

- **`manifest.gate` n'est écrit que par ce runner** (AD-7). L'ingestion ne l'écrit jamais et le conserve tel quel quand elle réécrit une entrée. Le gate porte le `source_hash`, l'`ingest_fingerprint` et l'`overlay_hash` **de l'entrée du manifest** : les recalculer donnerait un gate qui se valide lui-même.
- **Un document est servi ssi aucun bloquant statique et (`gate.evals_ok` ou `ENV=dev` ou `ALLOW_UNGATED`)** (AD-8). Les deux moitiés sont appliquées par le loader : il relit `report.json` pour le seul niveau `bloquant`, et compare le gate à l'entrée. Un rapport absent ou illisible n'est **pas** un bloquant (AD-8 en fait un artefact d'ingestion ; l'illisibilité est dite par l'alerte `rapport_illisible` de `/sante`).
- **`ALLOW_UNGATED` est fermé en production** : le `Dockerfile` ne l'arme plus, et en `prod` `config.py` force `allow_ungated=False` — poser `ALLOW_UNGATED=true` sur le service ne l'arme pas (AC 1.10). Le refus n'est pas muet : l'alerte `ungated_refuse_en_production` paraît sur `/api/v1/sante` et un avertissement part au journal de démarrage. La dérogation ne vaut plus qu'en `ENV=dev` ; en production, un gate invalidé se répare en relançant les témoins (`--gate`).
- **Le plafond de coût est par run**, pas par requête (AD-9) : `evals_max_cost_eur` dans `config.py`, surchargeable par `--max-cost`. Le runner s'arrête **avant** le cas qui le dépasserait, sans toucher au manifest.
- **Un gate que le schéma ne sait plus lire se reprend aussi.** Quand `Gate` gagne un champ obligatoire, tous les gates déjà écrits deviennent des entrées de manifest invalides : leur document part en quarantaine, et `--gate` refuserait « document non servi » — le blocage même que la reprise d'un gate rouge évite, par une autre porte. Pour le seul document visé, et en lecture seulement, un gate que l'image ne sait pas lire est donc traité comme absent ; à l'écriture, les autres entrées sont recopiées telles quelles, leur gate périmé compris, et leur propre `--gate` le refera.
- **Un gate rouge se reprend.** Un run qui écrit `evals_ok: false` met le document en quarantaine `gate_echoue` (AD-8 : « jamais servi »). Le runner sait malgré tout le re-mesurer : `--gate {doc_id}` lit alors un manifest **de lecture** où le seul gate de ce document vaut `null` (dossier temporaire de liens symboliques ; `data/` n'est pas touché). Un verdict d'éval ne doit pas rendre l'éval impossible. Tout le reste d'AD-7 continue de s'appliquer : hashes, overlay, bloquant statique, `status: quarantaine`.
- **Quand faut-il relancer les gates ?** Dès que `pipeline_digest`, `prompts_digest` ou `model_ids` bougent — c'est-à-dire dès qu'on touche `server/app/{steps,pipelines,corpus,llm}/` ou un prompt. Sans cela, le serveur sert les documents avec l'alerte `gate_perime` pendant que `/` continue d'annoncer leur profil. `tests/test_digests.py::test_les_gates_du_depot_sont_ceux_de_limage_courante` rougit dans ce cas et donne la commande ; deux runs coûtent ≈ 0,10 € et demandent la clé.
- **Ce qui n'est pas livré est refusé, jamais approximé** : le profil `full` (story 4.1), la suite `parsing` (story 4.2), le cache de réponses, les baselines, le holdout, `docs/evals/latest.md` et `GET /api/v1/evals/latest` (4.1/4.5). Le message nomme la story.
- **`server/evals/` n'est jamais importé par `server/app/`** (`tests/test_layers.py` le vérifie statiquement) : le système mesuré ne dépend pas de ce qui le mesure. Le runner construit corpus, index et client exactement comme `api/etat.py` le fait pour les routes.
- **`pyyaml` est une dépendance de développement seule** : l'image est construite avec `uv sync --frozen --no-dev` et ne la reçoit pas.

## L'accueil

`tools/accueil/` (story 1.10). Servi sur `/` par le montage statique ; vanilla, sans build, sans framework, sans requête tierce, sans `localStorage`.

- **Trois entrées** (`/guide/`, `/sinistre/`, le sujet 3), **la réponse écrite au sujet 3** — « je ne fais pas un RAG » : la table va dans une base SQL, on filtre d'abord, le modèle traduit la question en requête (schéma + échantillon de valeurs, requête **affichée**, lecture seule, `LIMIT`, timeout) et ne calcule rien, le texte libre n'est cherché qu'**après** le filtre et sur les colonnes de texte, un profil par colonne est calculé à l'ingestion, et la restitution montre la requête, le nombre de lignes, les lignes sources et ce que les données ne disent pas — et les liens vers le dépôt.
- **Le niveau de validation est lu, jamais écrit** : `accueil.js` sonde `GET /api/v1/sante` et compose une phrase depuis `gate_profile`, `gate_cases` et `gate_countersigned`. « 2 cas » n'est écrit nulle part dans la page — un test le vérifie en servant un gate à un cas et en attendant « 1 cas relu ».
- **« Relus à la main » n'est écrit que si une main les a relus.** AD-14 définit `vertical` par une relecture humaine, et la page l'affirme publiquement : la qualification vient donc de `gate_countersigned`, pas du nom du profil. Tant que la contresignature est due, la page écrit « N cas relus par la boucle, contresignature humaine en attente » et le badge du guide porte « non contresigné ». Pour la lever : remplir `truth.countersigned_by` (nom + date) dans les deux YAML et relancer les deux `--gate` — `cases_hash` change.
- **Trois états, et trois seulement** : la sonde répond avec un profil (« niveau de validation : vertical — N cas », qualifié « relus par la boucle, contresignature humaine en attente » tant que `gate_countersigned` est faux et « relus à la main » une fois la contresignature portée dans les cas — c'est l'état d'attente qui est celui du dépôt aujourd'hui —, plus les alertes) ; elle répond sans profil (« aucun gate » + pourquoi) ; elle ne répond pas (« inconnu — le serveur n'a pas répondu »). Le troisième n'affiche **jamais** le dernier profil connu ni un défaut optimiste. Un 200 que la route n'aurait pas pu écrire — clé absente, `gate_profile` sans `gate_cases` ou sans `gate_countersigned` — est traité comme une sonde en échec, pas comme un niveau à moitié lu.
- **Elle se teste sans navigateur** : composition pure (`lireSante`, `libelleValidation`, `vueEtat`, `vueAlertes`, `vueSondeEchouee`) et matérialiseur `textContent` sans décision ; `tests/js/accueil_cases.mjs` dans un `node:vm`, `tests/test_web_accueil.py` pour les assertions.

## Ingestion du guide

```bash
uv run python -m server.ingest.kb_to_blocks        # data/lux-guide/source.js → document.json, summary.md, report.json ; fusion de data/manifest.json
```

- `data/lux-guide/source.js` est la copie octet-identique de `web/app/kb.js` (filiation dans `data/lux-guide/README.md`) ; le parseur est en Python pur, sans Node.
- Sortie déterministe : relancer ne modifie rien ; `document.json` ne contient jamais `text_norm`, recalculé au chargement.
- Exit 1 et `status: quarantaine` dans `manifest.json` si un check bloquant (invariant d'arbre) est levé ; `ids_disparus` est une alerte calculée contre le `document.json` précédent.
- `manifest.gate` reste `null` jusqu'au premier gate des questions-témoins (story 1.10) ; en dev, `ALLOW_UNGATED` sert le document avec l'alerte `sans_gate`.
- Le serveur lit `data/` par `server/app/corpus/loader.py` (hashes recalculés, quarantaine par document) et l'indexe par `server/app/corpus/index.py` ; les seuils (`search_limit`, `node_window`) viennent de `server/app/config.py`.

## Dictionnaire enrichi

`data/dictionary.json` donne à *retrouver* les **variantes** d'un terme (français familier, anglais, allemand, portugais) et arme, une fois validé à la main, le refus « zéro hit » d'AD-5. Il est écrit par l'ingestion, lu par le serveur au démarrage, et committé (AD-7).

```bash
uv run python -m server.ingest.enrich_dictionary --dry-run        # le plan des requêtes et le majorant de coût, rien d'écrit
uv run python -m server.ingest.enrich_dictionary                  # écrit data/dictionary.json, validated: false
uv run python -m server.ingest.enrich_dictionary --valider "Nom"  # la signature humaine, et la seule chose qui arme le refus
```

- **Une requête de batch par catégorie du guide**, plus une pour les déclencheurs d'intention (tier `ingest`, Batch API, sortie structurée). Une requête par fiche multiplierait par quatre le majorant de sortie sans rien apporter. Le **majorant du run entier** est calculé avant toute soumission et comparé à `dictionary_max_cost_eur` : au-delà, aucun batch n'est soumis (exit 3) — le run refuse de démarrer plutôt que de découvrir la facture après coup. Les résultats sont agrégés par `custom_id`, jamais par position.
- **Le code ne fait pas confiance au modèle** (AD-5 / AD-7 / FR29 : il ne renvoie jamais de texte de bloc). Chaque chaîne rendue passe les bornes de `config.py` (`dictionary_term_max_chars`, `dictionary_term_max_words`, `dictionary_question_max_chars`, …) et le contrôle « chaîne recopiée d'un bloc » ; hors borne, elle est **écartée, jamais tronquée**, et le compte des écarts est affiché en fin de run. Un `fiche_id` que la catégorie ne contient pas est écarté de même.
- **Deux verrous distincts, publiés par `/api/v1/sante` et affichés sur `/`** : `corpus_ok` (les `corpus_source_hashes` du fichier décrivent le corpus servi) commande l'emploi des **variantes** par *retrouver* ; `validated ∧ corpus_ok` — c'est `refus_zero_hit_actif` — commande le **court-circuit** d'AD-5. Élargir la recherche n'affirme rien et chaque phrase affichée reste vérifiée contre le corpus (AD-3) ; **refuser** est une affirmation négative, visible et irréversible pour celui qui la reçoit : c'est elle que la signature humaine garde.
- **Ce que la non-validation désarme, et rien d'autre** : le court-circuit « zéro hit » **avant** *retrouver*. Le refus par intent reste actif, les variantes servent, et une question sans aucun hit est refusée quand même — par le garde-fou « zéro bloc » de la story 1.5, avec la même preuve. Ce qui distingue les deux est observable : la présence de l'étape `retrouver` dans la trace.
- **`--valider "Nom"` écrit trois champs et ne touche à aucun autre** (`validated`, `validated_by`, `validated_at` en UTC ISO 8601), et refuse (exit 5) si le fichier ne décrit plus le corpus livré. C'est un commit `data` dédié. Rien dans l'ingestion n'écrit jamais `validated: true`.
- Un dictionnaire absent, illisible, non conforme ou d'un autre corpus **désactive une optimisation, il n'empêche jamais de servir** et ne lève jamais au démarrage (AD-7) ; il est **dit** — alertes `dictionnaire_non_valide` / `dictionnaire_corpus_perime` sur `/api/v1/sante`, ligne « dictionnaire des variantes » sur l'accueil, `CheckResult(dictionnaire)` dans la trace de *retrouver* (AD-16 : aucun dégradé silencieux).
- **`intents` et `candidate_questions` sont produits, versionnés — et lus par personne**, délibérément (`target_story: 2.5`). AD-5 est explicite : « les déclencheurs d'intention sont distincts des mots du corpus — la présence d'un mot n'est jamais une preuve de pertinence » ; refuser une question parce qu'elle contient « météo » ferait exactement ce que cette phrase interdit, et le refus par `intent`, décidé par *comprendre* qui a lu la question entière, est déjà en place et suffit. Les deux champs existent pour servir de **mesure** en 2.5 (« pourquoi cette réponse ») : confronter l'`intent` rendu aux déclencheurs pour dire quand les deux divergent, sans jamais laisser les seconds trancher ; et proposer des questions candidates, qui est une décision d'interface.
- Les consignes d'ingestion vivent sous `server/ingest/prompts/` et **non** sous `server/app/llm/prompts/` : y entrer les mettrait dans `prompts_digest`, et modifier une consigne d'ingestion rendrait les deux gates `gate_perime` pour un prompt que le serveur n'exécute jamais.
- Le périmètre annoncé à *comprendre* (`Corpus.perimetres`) est une projection des titres du corpus, calculée au chargement et bornée par `perimetre_max_chars` : une fiche ajoutée entre dans le périmètre sans qu'on réécrive une phrase de prompt.

```bash
uv run python -m server.ingest.fetch_source axa-lu-optihome-2017   # source.url + source.sha256 → source.pdf (non committé)
uv run python -m server.ingest.pdf_to_blocks axa-lu-optihome-2017  # source.pdf → document.json, summary.md, report.json ; manifest fusionné
```

- Le PDF n'est **pas redistribué** : `fetch_source` le télécharge depuis `source.url` (URL publique d'AXA, ou `gs://bucket/objet` du bucket privé), vérifie le sha256 de référence (`source.sha256`) et se replie sur `gs://foyer-retour-sources/` si la source est morte ; hash différent ⇒ exit 2 sans rien écrire, repli en échec ⇒ exit 3. Le `Dockerfile` exécute `fetch_source --all` au build. En local, les objets `gs://` sont lus avec le jeton `GOOGLE_OAUTH_ACCESS_TOKEN=$(gcloud auth print-access-token)`. `pdf_to_blocks` exige `source.sha256` et le compare au PDF avant toute extraction.
- `pdf_to_blocks` (PyMuPDF, `get_text("dict", sort=True)`) : un bloc par paragraphe/liste/titre avec `page`, `lines` (`line_id`, `text`, `bbox`) et `bbox` = union ; en-têtes et numéros de page retirés ; nœuds construits par la numérotation des articles (`a1.12`, `a3.1.1.1.6`, parent = préfixe le plus long) ; `scope.kind` : `1`, `2`, `3.1` ⇒ `commun`, `3.1.8` ⇒ `extension`, le reste ⇒ `special` ; un paragraphe ou une liste à cheval sur deux pages est scindé, le second bloc porte `continues` (règle structurelle : même kind, pas de numéro d'article, phrase non terminée). Les signets du PDF (`get_toc()`), s'il y en a, donnent leur titre aux nœuds qui n'en ont pas et sont confrontés à la numérotation (`tdm_pdf_ecart`). Texte brut, seules altérations déclarées dans `FLAGS` (puces `•`, glyphe de tabulation retiré, espaces de fin et de tête de ligne, numéro d'article joint par une espace à son titre).
- `report.json` (AD-8) : `page_sans_texte` (page portant une image ou un tracé vectoriel mais aucun texte : bloquant ⇒ quarantaine), `numerotation_non_monotone`, `numerotation_dupliquee`, `pages_mixtes`, `tdm_pdf_ecart`, `ids_disparus` (alertes), statistiques (pages, blocs par kind, `continues`, en-têtes retirés, TdM du PDF).
- `data/axa-lu-optihome-2017/typing.manual.json` : typage manuel des clauses (`kind`, `defines`, `scope_node_id`, `scope_node_ids`, `kind_source=manual`), fusionné par le loader **avant** validation sans modifier `document.json` ; `schema_version`, `doc_id` et `kind` sont obligatoires ; un `block_id` ou un nœud inconnu, un `kind_source` ≠ `manual` ou un champ inattendu met ce seul document en quarantaine. Son empreinte est écrite dans `manifest.json` (`overlay_hash`) par l'ingestion et vérifiée par le loader, et elle fait partie de ce que le gate des témoins couvre. `scope_node_ids` restreint la portée d'une clause à une partie du sous-arbre de `scope_node_id` (l'exclusion p. 46 ne vise que les extensions 3.1.8.3 à 3.1.8.6 ; `Document.scope_nodes(block_id)` donne les nœuds couverts). Remplacé par le typage automatique (Epic 3).
- Les seuils d'ingestion (`header_band_pt`, `footer_band_pt`, `header_min_pages_ratio`, `para_gap_ratio`, `article_number_max_x`, `title_min_size_pt`, `header_caps_max_size_pt`, `baseline_tolerance_pt`, `number_gap_tolerance_pt`, `list_indent_pt`, `fetch_timeout_s`, `metadata_timeout_s`) vivent dans `server/app/config.py` ; ceux qui changent la segmentation entrent dans `ingest_fingerprint`.
- `tests/test_parsing_axa.py` compare les pages 9, 11, 34 et 46 à des extraits relus (`tests/data/axa/`) contre le `document.json` committé ; si `source.pdf` est présent, l'ingestion doit le regénérer à l'identique.
- Les artefacts de tous les documents sont écrits sans valeurs par défaut ni `text_norm` (`SCHEMA_VERSION=3`, `server/ingest/artifacts.py`). La version du schéma entre dans **chaque** `ingest_fingerprint` : l'incrémenter ré-ingère les deux documents et périme les deux gates. `"3"` ajoute `Document.parcours` — les conditions de profil que la `timeline` du guide attache à ses fiches (story 2.3), vide pour un contrat.

## Client LLM

Le client Claude unique des étapes vit dans `server/app/llm/` (story 1.3) ; aucune étape n'appelle le SDK directement.

- `models.py` : `TIERS` (`ingest` = Opus 5 Batch, `reason` = Sonnet 5 cache 1 h, `micro` = Haiku 4.5 daté), `STEP_TIERS`, `MODEL_CAPS` (effort/temperature/TTL par modèle), `EFFORT`, `model_for(tier)` ; `--check` vérifie les IDs contre l'API.
- `pricing.py` : la seule table de prix (USD/MTok, lecture de cache 0,1×, écriture 1,25× en 5 min / 2× en 1 h, `BATCH_DISCOUNT=0.5`) ; `cost_from_usage` chiffre en euros **uniquement** depuis l'`usage` renvoyé par l'API ; `estimate_cost` est la borne haute avant appel (préfixe et schéma de sortie au tarif d'écriture de cache du TTL du modèle, messages au tarif d'entrée, sortie à `max_tokens`, caractères par token calibrés sous le pire mesuré).
- `budget.py` : `RequestBudget(deadline_s, max_attempts, max_cost_eur)` — deadline monotone, compteur d'appels et cumul de coût partagés par toutes les étapes d'une requête.
- `prompting.py` + `prompts/` : `untrusted(kind, text)` délimite le contenu non fiable (balise fermante neutralisée), `load_prompt` lit les prompts versionnés (`commun.md` : règles de non-confiance) couverts par `prompts_digest`.
- `client.py` : `LlmClient.parse(tier, system_prefix, messages, output_model, budget, step, …)` — sorties structurées (schéma Pydantic), bloc système unique avec `cache_control` (préfixe byte-identique), timeout = min(`llm_timeout_s`, deadline restante), 1 retry sur parse invalide si la marge le permet, plafonds d'appels et de coût **avant** l'appel, mapping exhaustif des erreurs SDK vers `LlmUnavailable` (ou `Timeout` pour `APITimeoutError`) — `LlmParse` (parse invalide après retry, refus) et `BudgetExceeded` (plafonds) sont produits par le client lui-même, jamais mappés depuis une erreur SDK —, chaque appel tracé en `LLMCall` — y compris l'appel en échec (timeout, 429, 529, réseau : usage nul, durée réelle) ; `ResponseCache` (protocole) + `MemoryResponseCache` pour le cache d'évals ; `count_tokens` au tokenizer réel.
- `python -m server.app.llm.tokens <fichier…>` : tokens réels d'un fichier par tier (a servi à compacter les sommaires, voir `docs/tests-live.md`).
- `tests/test_client_live.py` fait un appel réel par tier quand la clé est là (fixtures brutes committées dans `tests/llm_fixtures/`, rejouées sans clé).

## Étapes du pipeline

Les étapes vivent dans `server/app/steps/` (stories 1.4 et 1.5). Chacune est une fonction `Entrée → Sortie` qui crée et renvoie **son** `StepTrace` ; aucune étape n'en importe une autre (`tests/test_layers.py`), et `steps` ne connaît que `domain`, `corpus`, `llm`, `config`. L'enchaînement, les court-circuits et la relance sont l'affaire du pipeline (ci-dessous).

- `comprendre.py` — un appel `micro` : question + historique + profil → **deux sorties typées exclusives** (AD-5) : `ParsedQuestion` (intent, question résolue **autonome**, langue, termes toujours en français, `scope` dérivé du profil déclaré), ou `ClarificationRequise` quand une anaphore reste irrésoluble avec l'historique — dans ce cas aucune `question_resolue` n'est construite, ni inventée ni reprise telle quelle, et c'est la question à poser à l'utilisateur qui est rendue. Le modèle répond dans un schéma plat à champs requis, converti ensuite dans le modèle du domaine : un schéma sans valeur par défaut force le modèle à tout remplir, et l'exclusivité des deux issues y est un invariant — sa violation emprunte la relance motivée du client plutôt qu'un arbitrage du code. `lang` explicite l'emporte sur la détection et n'accepte que `fr`, `en`, `de`, `pt` ; une valeur hors liste est refusée avant l'appel. Sans forçage, une détection illisible ou non servie retombe sur `fr` avec `lang_fallback=true`. Le préfixe système est statique (`prompts/commun.md` + `prompts/comprendre.md`) — pas de sommaire, l'intent et les termes n'en ont pas besoin. Mesuré en live : ce préfixe (≈ 900 tokens) est **sous la taille minimale cacheable de Haiku 4.5** (2 048 tokens), donc jamais mis en cache — c'est pourquoi le client ne compte un préfixe au tarif de lecture que si le fournisseur confirme l'avoir caché.
- `retrouver.py` — deux implémentations sous le même contrat. `outils` est le défaut ; son tier `micro`, ses deux tours maximum et sa sortie de 1 024 tokens sont configurés pour garder le chemin froid sous 0,10 €. Il navigue avec exactement `sommaire`, `chercher`, `ouvrir_noeud` et `definitions`, puis s'arrête dès le premier tour qui a admis des blocs sans pagination. `deterministe` reste du **code pur, zéro appel modèle**, sert de baseline explicite et reprend une navigation outils tronquée sans bloc. Les deux variantes relisent les mêmes `Block` du corpus, appliquent les mêmes budgets `max_opens`/blocs/tokens, suivent un seul niveau de renvois et de définitions, et produisent le même `RetrievalResult`. La trace publie le tier réellement appelé et `calls=[]` distingue le déterministe. La variante outils refuse tout `focus_block_id` absent des candidats réellement rendus par `chercher`, ne considère un zéro-hit complet qu'après couverture de tous les termes canoniques, et transmet aux outils seulement `block_id` + `text`. Le choix ne change ni la chaîne, ni le préfixe, ni les schémas de *rédiger* ; son appel reçoit toutefois le plafond dédié `outils_rediger_max_tokens=1792`, contre 2 048 tokens sur la baseline, afin de borner le chemin froid.
- `rediger.py` — un appel `reason`, sortie `AnswerDraft`. Préfixe cacheable 1 h byte-identique = `prompts/commun.md` + `prompts/rediger.md` + **sommaire versionné** du document ; historique, blocs (**précédés de leur `block_id`**) et question résolue viennent après le breakpoint, chacun délimité par `untrusted()`. La consigne finale nomme la langue de rédaction en clair et impose que les quotes restent recopiées mot pour mot dans la langue du bloc. Les invariants du domaine (`claim_id` uniques, `claim_ids` connus, segment `factuel` ⇒ au moins une claim, une quote par bloc) sont validés **au parse** : un draft incohérent déclenche la relance motivée du client, puis `LlmParse`. `motif` (relance de la story 1.5) s'ajoute au dernier message utilisateur, lui aussi délimité par `untrusted()`. Les bornes chiffrées annoncées au modèle (`quote_min_chars`, `quote_max_chars`, `draft_max_segments`, `draft_max_claims`) sont rendues dans le prompt depuis `config.py` (`prompting.render_prompt`) : régler un seuil ne peut plus désynchroniser ce que le modèle produit et ce que le code acceptera. *Rédiger* refuse un `doc_id` qui ne recouvre pas les blocs reçus, avant tout appel : le sommaire du préfixe situe les blocs, il ne peut pas venir d'un autre document.
- Coût : `comprendre_max_tokens` et `rediger_max_tokens` bornent la sortie de chaque appel, `retrieval_max_blocks` et `retrieval_max_tokens` bornent ce que *retrouver* envoie à *rédiger* — ce sont les postes qui font tenir la chaîne sous le plafond de 0,10 € par requête, majorant `estimate_cost` compris. `RequestBudget` mémorise les préfixes déjà écrits dans la requête : un second appel au même préfixe est estimé au tarif de lecture de cache (0,1×) et non d'écriture.
- `verifier.py` — le contrôle, en deux moitiés. **Code pur** d'abord, pour chaque quote : le `block_id` existe, le bloc n'est pas un `heading`, la quote normalisée fait au moins `quote_min_chars` (ou `quote_min_ratio` du bloc), elle est **incluse** dans le `text_norm` du bloc **relu depuis le corpus** — jamais le texte du draft —, et son occurrence n'est pas ambiguë (le même passage dans un second bloc du document attribuerait la phrase au mauvais endroit). Les offsets de l'occurrence et les `line_ids` traversés sont conservés pour le surlignage. Une claim est `retrouvee` **ssi toutes** ses quotes le sont. **Un seul appel `micro` groupé** ensuite, sur les seules claims retrouvées : « ces passages soutiennent-ils l'affirmation **et** répond-elle à la question ? » — le modèle ne rend qu'un booléen par `claim_id`, aucun texte libre. `found` et `complete` sont calculés **par le code** (AD-4). Un verdict manquant n'est jamais deviné : la claim est écartée et un `CheckResult` le dit. Rien de ce qui vient du modèle ne traverse un motif en clair : un `block_id` inconnu du corpus devient `<bloc inconnu>` ; un `block_id` connu, lui, est notre propre chaîne, et c'est ce qui rend la relance actionnable.
- `restituer.py` — aucun modèle (AD-9). `Answer.texte` est rendu **déterministement** depuis les segments survivants : un segment `factuel` dont toutes les claims ont été rejetées est retiré, et les `claim_ids` des segments conservés sont ramenés aux claims survivantes. Un refus rend un unique segment `limite` porteur d'une phrase composée par le code — une par `kind` d'`AbsenceProof`, pour que « hors périmètre » ne se confonde pas avec « rien trouvé » ni avec « rien qui tienne la vérification ». Les constats du code sont des `Lacune(kind, n)` jusqu'à cette étape, qui les rend depuis un registre complet `fr/en/de/pt`, comme les quatre motifs de refus des registres guide et sinistre. Un refus conserve donc la langue servie ; `lang_fallback` ne signifie plus qu'un repli de détection.
- `tests/test_steps_live.py` rejoue trois scénarios réels sur le corpus `lux-guide` (profil famille → `scope`, question météo → `intent` seul, chaîne complète → ébauche citée sur deux fiches).

## Le pipeline du guide

`server/app/pipelines/guide.py` (story 1.5) enchaîne les cinq étapes — *comprendre → retrouver → rédiger → vérifier → restituer* — et rien d'autre. La couche `pipelines` **ne voit ni `corpus` ni `llm`** (table des couches du spine, vérifiée par `tests/test_layers.py`) : le corpus, l'index et le client lui arrivent en paramètres. Ce n'est pas un renoncement au typage, c'est l'invariant lui-même — un pipeline qui ne peut pas importer `llm` ne peut pas appeler un modèle hors d'une étape, ni sauter la vérification.

Ce qu'il ajoute aux étapes :

- **Les bornes d'entrée.** Le `RetrievalBudget` est rempli depuis `config.py` (`max_blocks`, `max_tokens`) ; un historique de plus de `historique_max_turns` tours est **refusé**, jamais tronqué (`InvalidRequest`, avant le premier appel : une requête refusée ne coûte rien) ; la deadline monotone est vérifiée avant chaque étape.
- **Les court-circuits.** Un `intent` hors périmètre, une clarification requise ou un retrieval vide vont directement à *restituer*, **sans** appel `reason`. Le court-circuit « zéro bloc » est distinct de celui d'AD-5, fondé sur le dictionnaire, qui reste désactivé tant qu'aucun humain n'a validé `data/dictionary.json` (story 2.1) : ici *retrouver* a bel et bien cherché, et l'`AbsenceProof` dit ce qui l'a été — jamais que l'information n'existe pas.
- **La relance, une seule fois.** Un défaut de **citation** (quote introuvable, bloc `heading`, quote trop courte, citation ambiguë) relance *rédiger* avec le motif précis composé par *vérifier* ; une ébauche identique (même hash canonique) arrête là. Une claim écartée par le seul jugement de pertinence ne déclenche pas de relance quand la réponse tient déjà : elle est conservée dans `rejected_claims[]`, et un second appel `reason` coûterait le tiers du budget d'une requête (seuil `relance_sur_non_pertinence`, à mesurer avec les questions-témoins). Quand **rien** n'a survécu, la relance part de toute façon : elle est le seul chemin vers une réponse.
- **Une relance qu'on ne peut pas payer ne jette pas la réponse.** AD-1 dit « aucun retry ne démarre sans marge » ; la même règle vaut pour les euros. Si le plafond par requête ou la deadline arrêtent la relance, la **première** vérification fait foi et la trace porte `relance_abandonnee`. Un draft relancé mais non vérifié n'est jamais montré.
- **La trace.** Étapes, tiers, durées, usage et coût réel, blocs ouverts et écartés, contrôles, seuils actifs, digests du pipeline et des prompts, `source_hash` et `ingest_fingerprint` du document — et **jamais** le texte d'un bloc.

Toute sortie normale — réponse, refus, clarification, claims toutes rejetées — est un `Answer` complet ; seules les entrées hors bornes et les échecs terminaux des étapes remontent en exception (l'API en fera des 4xx/503 en story 1.6). `tests/test_pipeline_live.py` rejoue deux scénarios réels : une question du guide dont chaque phrase affichée est soutenue, et un refus météo qui n'atteint jamais l'étage `reason`.

## Le verdict de sinistre

`server/app/domain/verdict.py` (story 1.8) est le découpage d'exécution d'AD-6 : **le modèle extrait des valeurs typées, le code décide.** Le module ne connaît ni le corpus, ni le client, ni les étapes — un test de couches le verrouille —, ce qui rend la table jouable ligne par ligne sans réseau (`tests/test_verdict.py`).

- `applicable_de_claim()` dérive `ClaimStatus.applicable` d'une claim retenue : `None` si elle ne cite aucune clause décisionnelle (une définition n'a pas d'applicabilité) ; `humain` si le `kind` d'un bloc cité n'est pas confirmé, si la clause n'a pas de portée déclarée, ou si les champs typés n'ont pas été rendus — **jamais** une valeur devinée. Vient ensuite la seule distinction qui fait tout le travail : `fait_requis_present=false` **sans** `fait_manquant` veut dire que le fait est *connu et contraire* — la clause ne vise pas ce cas —, tandis qu'un `fait_manquant` renseigné veut dire que le fait est *inconnu*. La première lecture n'est ouverte qu'aux `garantie` et `exclusion` : sur une `condition` ou une `franchise`, elle ne se distingue pas de « la condition n'est pas remplie », et la traiter comme inapplicable laisserait passer un `couvert` sur un dossier en défaut.
- `decider()` applique la table exclusive, dans l'ordre : contradiction déclarée par le corpus (`Block.relation.contredit` entre deux claims **affichées**) ou renvoi non résolu sur une claim décisionnelle ⇒ `ne_tranche_pas` ; aucune claim affichée de kind `garantie` ou `exclusion` ⇒ `ne_tranche_pas` ; exclusion `oui` dont la portée (`Document.scope_nodes()`) couvre les nœuds du cas ⇒ `non_couvert` ; garantie `oui` avec une condition ouverte ou hors du socle (`Node.scope.kind == "commun"`) ⇒ `sous_conditions` ; garantie `humain` **par** une option ou les conditions particulières ⇒ `sous_conditions` ; garantie du socle `oui` et rien d'ouvert ⇒ `couvert` ; sinon `ne_tranche_pas`. Le verdict porte sur les claims **affichées**, après le filtre `non_citee` d'AD-4 : un verdict adossé à une clause que l'utilisateur ne voit pas contredirait « rien d'affiché sans preuve ».
- **Ce qui empêche un `couvert` de complaisance est du code, et il a été mesuré.** La table peut rendre `couvert` — c'est une garantie du socle qui s'applique, aucune clause ouverte —, mais un `couvert` ne dit jamais que le sinistre sera indemnisé : il dit qu'aucune clause des conditions générales retrouvées ne s'y oppose. `MissingPackage` accompagne donc **tous** les verdicts, `couvert` compris, et `ask_client` réclame les quatre pièces qui n'ont pas été lues. Ce qui corrobore le `oui` d'une garantie n'est pas une politique globale mais l'établissement des qualités que la clause exige : le modèle **énumère** ces qualités et, pour chacune qu'il dit établie, cite un fragment des faits déclarés ; le code relit ce fragment mot pour mot dans les faits **et** exige qu'il emploie les mots de la qualité. Mesuré sur deux runs réels du cas témoin : le modèle a cité trois fois le même fragment — « Une bougie allumée posée sur une table basse est tombée sur le canapé » — pour établir « caractère soudain », « action subite de la chaleur » et « contact direct avec un foyer ». Authentique, et n'établissant aucune des trois : le code les refuse toutes, la garantie vaut `humain`, et les trois qualités partent en questions au client. Un modèle qui n'énumère rien rend son jeu de champs typés inexploitable — jamais un `oui` par défaut.
- `reason`, `ask_client[]` et `escalate[]` sont **composés par le code** depuis la règle qui a tranché et les booléens typés. Une question par pièce du paquet manquant (options, conditions particulières, avenants et date d'effet) : les annoncer absentes sans les demander laisserait le gestionnaire deviner. Seuls les libellés de `fait_manquant` viennent du modèle — bornés par `fait_manquant_max_chars` (au-delà, ignorés, jamais tronqués : une demi-phrase de fait manquant induit en erreur), dédupliqués, et bornés en nombre par la place que les questions du paquet laissent dans `ask_client_max`, pour que `missing.faits` et `ask_client` disent la même chose. Ils n'entrent jamais dans `Answer.texte`.

## Le pipeline du sinistre

`server/app/pipelines/sinistre.py` (story 1.8) rejoue **les cinq mêmes étapes**, dans le même ordre : le sinistre n'en fabrique aucune. Ce qui change tient aux consignes, au document et au verdict.

- **Les prompts.** `comprendre_sinistre.md`, `rediger_sinistre.md` et `verifier_sinistre.md` s'ajoutent à `prompts/` ; les étapes gagnent un paramètre `prompt` dont le **défaut est le guide**, si bien que son préfixe reste byte-identique et ses fixtures live rejouables. *comprendre* reçoit en plus les `Faits` déclarés (AD-5 les nomme déjà), délimités par `untrusted()`. *rédiger*, lui, ne les voit pas : ils lui arrivent repliés dans la question résolue, et le prompt le dit.
- **Un seul appel `micro`, toujours.** `SortieVerifierSinistre` hérite de `SortieVerifier` et ajoute `applicabilite[]` : pertinence, phrases soutenues, couverture des facettes et champs typés sortent du **même** appel (AD-9 amendé — « jamais un second appel »). Son plafond de sortie est distinct (`verifier_sinistre_max_tokens`) parce qu'il rend une entrée de plus par clause : à `verifier_max_claims` claims, le partager avec le guide ferait tronquer la réponse, donc un `LlmParse`, donc un sinistre **sans verdict**. Le schéma n'offre au modèle aucune place pour un verdict : ni `applicable`, ni `couvert`, ni `value`.
- **Une seule clause par affirmation** (AD-6). Le contrôle est en code, sur le typage de l'ingestion : une claim dont les blocs cités portent deux `kind` décisionnels différents est rejetée `ambigue` avec un motif actionnable — donc elle emprunte la relance unique d'AD-3. Une clause jointe à sa définition ou à son paragraphe d'introduction reste admise : c'est son contexte.
- **La recherche préfère les clauses, elle ne s'y limite pas.** `Index.chercher(kinds_prioritaires=…)` place les blocs `garantie|exclusion|condition|franchise` devant les autres **à score égal** — le départage vit dans l'index parce que le score n'existe que là. Il ne filtre par aucun kind, mais il change qui survit à `limit`. À J+1 le typage est manuel et ne couvre que quatre blocs du contrat : le rappel repose encore surtout sur les termes, et c'est le typage automatique (epic 3) qui lèvera la limite.
- **Aucun repli, et jamais un refus muet** (AD-16). Une variante inconnue, des faits hors bornes ou mal formés, un budget et une deadline passés ensemble sont des `InvalidRequest` levées **avant** le premier appel facturé ; un contrat non servi est un `CorpusUnavailable`. Et tout refus — hors périmètre, aucune clause trouvée, toutes les citations rejetées — porte un verdict `ne_tranche_pas` composé par le code, avec les questions du paquet manquant : c'est le dossier qui a le plus besoin d'être complété. *restituer* choisit son **registre** de phrases (`REGISTRE_SINISTRE`) pour que le refus parle du contrat et non du guide.
- Les invariants de relance partagés par les deux pipelines — dominance sur tous les axes, deux appels indissociables, motifs de citation — vivent dans `server/app/pipelines/commun.py`. Le `Verdict` n'entre pas dans la comparaison : ses quatre valeurs n'ont pas d'ordre, et préférer une relance pour ce qu'elle conclut serait exactement ce qu'AD-6 empêche.
- `tests/test_sinistre_live.py` rejoue le cas témoin de la bougie sur le contrat AXA réel, enregistré puis rejouable sans réseau ; le relevé est dans `docs/tests-live.md`. La route HTTP et la page `/sinistre/` sont la story 1.9.

## Le serveur HTTP

`server/app/api/` (stories 1.6, 1.9 et 1.10). **Une seule origine** sert tout (AD-12) : `/` (l'accueil, `tools/accueil/`), `/guide/` (la copie du site, fichiers jamais renommés), `/sinistre/` (l'outil sinistre), `/api/v1/chat`, `/api/v1/sante`, `/api/v1/sinistre`, `/api/v1/documents`, `/api/v1/documents/{doc_id}/report`, plus les alias historiques `/chat` et `/sante` attendus par `reponseApi()`/`testerApi()`. Aucune configuration CORS : il n'y a pas de seconde origine à autoriser.

- **Les routes du sinistre n'ont pas d'alias historique** (story 1.9) : AD-11 n'en prévoit que pour `/sante` et `/chat`, parce que le `chat.js` du site les attend. Rien n'attend `/sinistre` ni `/documents` à la racine, et un alias de plus serait une route inventée par story. `/documents` et `/report` ne coûtent rien (tout est chargé au démarrage) et ne sont donc **pas** limitées, comme `/sante` ; `/sinistre` l'est, comme `/chat`, par la même dépendance de routeur.
- **`POST /api/v1/sinistre`** rend `{answer, sources, via, trace}`. `sources[]` porte des `ClauseSource` : la citation relue du corpus, plus `page`, `bbox`, `line_ids`, `kind` et `kind_confirmed` **lus sur le bloc** (AD-6 : `Block.kind` est la seule source de typage — le front n'a pas de corpus et ne peut pas inventer le type d'une clause, ni taire qu'il n'est pas confirmé). Deux refus en 400 **avant tout appel facturé** : un `doc_id` que le service ne sert pas (le pipeline lèverait un 503, qu'AD-16 réserve à une indisponibilité passagère — or le corpus est chargé une fois et ne bouge plus), et un `doc_id` servi qui n'est **pas** un contrat (soumettre un sinistre au guide dépenserait quatre appels pour un `ne_tranche_pas` acquis d'avance). Le `dossier` du pipeline — ce que l'appelant détient déjà du paquet contractuel — n'est **volontairement pas** exposé par la route : sur un démonstrateur public, un booléen « j'ai les conditions particulières » est une auto-déclaration invérifiable qui referme la seule question que l'outil sait poser, et la promesse affichée est « au regard des conditions générales seules ».

- **Au démarrage, une seule fois** (`api/etat.py`) : les digests du pipeline et des prompts (ils relisent toute l'arborescence du code — les calculer par requête, ou les laisser au repli mémoïsé du pipeline, ferait servir des empreintes périmées sans que rien ne le dise), le `GateContext` de l'image, le corpus en lecture seule, l'index, le client Claude async. Une requête ne recharge rien.
- **Tout ce que le pipeline rend est un 200** (AD-11) : réponse, refus, clarification, affirmations toutes rejetées. Le corps porte `{texte, segments, sources, fiches, unknown, comparateur, answer, via: "api/v1", trace}`. `sources[]` ne contient que des citations **relues du corpus** (`VerifiedQuote`) — une citation que le validateur n'a pas retrouvée est restée la chaîne du modèle, et elle n'est pas affichée ; elle reste lisible dans `answer.rejected_claims`, où sa nature est explicite.
- **Les échecs sont terminaux, jamais dégradés** (AD-16) : une seule enveloppe `{error: {code, message, request_id}, trace?}`, les codes de `domain/errors.py` et rien d'autre. `400 invalid_request` pour une borne du contrat (question > 1 000 caractères, historique > 6 tours — **jamais tronqué** —, variante inconnue, ou `lang` hors de `fr/en/de/pt`), avant tout appel facturé ; `413 input_too_long` pour un corps HTTP au-delà de `request_max_bytes` (refusé avant d'être lu), `429 rate_limited`, `503` pour les pannes du pipeline (avec la trace partielle), `500 internal` générique pour l'imprévu. Un fichier statique absent reste un 404 nu : lui inventer un code serait précisément ce qu'AD-16 interdit.
- **Un identifiant par requête** (AD-10) : uuid4 posé par `api/request_id.py`, rendu en `X-Request-Id`, repris dans la `Trace` et dans l'enveloppe d'erreur. Une ligne JSON par requête sur la sortie standard, avec `intent`, `found`, `verdict`, `reason_kind`, `variants_count`, `blocks_scanned`, `cost_eur` — et **jamais** le texte de la question ni `terms_searched` (ils peuvent révéler santé, famille, argent). La liste des champs logués est close en code : une route ne peut pas la contourner. `X-Cloud-Trace-Context` est logué à part.
- **Le limiteur (`api/limiter.py`) est best-effort, par instance.** Il ne promet pas un quota global : ses compteurs vivent en mémoire de process (un redémarrage les remet à zéro, deux instances servent deux fois le quota), une adresse forgée par requête le contourne, et sa table est bornée (`rate_limit_max_clients`, la plus ancienne identité évincée repart de zéro). Ce qu'il protège, c'est le budget d'une démonstration servie par une seule instance — avec le plafond par requête (0,10 €) et le plafond fournisseur derrière lui. L'identité est le premier élément de `X-Forwarded-For`, lu directement dans l'en-tête (IPv4 entière, IPv6 tronquée au /64, parce qu'un abonné se voit déléguer un /64 entier). `Retry-After` annonce le reste de la fenêtre dépassée, borné par `retry_after_s`.
- `/sante` n'est jamais limitée (le front la sonde à chaque chargement de page) et publie ce qui a été calculé au démarrage : `ok`, `version` (`GIT_SHA`), `documents_servis`, `gate_profile` et `gate_cases` (**`null` tous les deux** dès qu'un document servi n'a pas de gate valide — annoncer un profil qu'un document ne porte pas serait une bascule silencieuse, et un compte sans profil serait la même, chiffrée), `dictionary.validated`, `alerts[]` (`sans_gate`, `gate_perime`, `source_absente`, `rapport_illisible`, quarantaine — dont `bloquant_statique` —, et `ungated_refuse_en_production`) et les seuils actifs.
- `comparateur` est calculé par la règle du site (`web/app/chat.js`, `toucheContrats`) transposée telle quelle sur la question normalisée : AD-11 le conserve « pour l'UI existante », et le laisser toujours faux retirerait une fonction du site en silence.

## Le front du guide

`web/` (story 1.7). La copie du site est servie sous `/guide/` ; seul son onglet **Assistant** a changé, et seulement là où le contrat d'AD-11 l'exigeait — aucun fichier renommé, aucun framework, aucune étape de build.

- **Il parle au serveur qui le sert** (AD-12) : `API_BASE` est l'origine courante, la sonde `/sante` tourne sur toute origine, le profil part **brut** (objet) et l'historique en `{role, texte}`, borné à six tours, le dernier tour utilisateur exclu quand il répète la question, un tour de plus de 2 000 caractères écarté plutôt que coupé. Le champ `contexte` de l'ancien relais a disparu : il recopiait plus de 20 ko de fiches que le serveur n'a jamais lues.
- **Il montre ce sur quoi il repose** (AD-3 / FR4) : chaque segment factuel est suivi de **ses** citations — le passage relu du corpus par le serveur, la fiche, le lien officiel, et le statut « retrouvée · pertinente · édition … — actualité non vérifiée ». L'appariement citation ↔ phrase refait l'énumération de `presenter.sources_de()` et vérifie chaque `block_id` ; au moindre désaccord il abandonne et montre la liste plate, plutôt que d'attribuer une citation à la mauvaise phrase (un test serveur verrouille cet ordre). Un refus affiche la phrase composée par `restituer` **plus** la preuve chiffrée d'AD-4. En pied : l'état (sûr / partiel / inconnu) et le coût réel lu sur `trace.total_cost_eur`.
- **Il dit ce qui est traduit** (story 2.4) : pour une réponse non française, le pied précise que la réponse est traduite depuis le guide français et que les passages cités restent dans leur texte source. Si la détection a dû retomber sur le français, une seconde mention le dit. `answer.lang` et `answer.lang_fallback` sont relus strictement ; un type cassé produit `reponse_illisible`, pas une réponse peinte à moitié.
- **Il n'a aucun repli silencieux** (FR11 / AD-16) : sur 503 ou panne réseau, un bandeau et un bouton à cliquer ; le moteur lexical du site ne tourne qu'après ce clic, et le résultat porte `via: "local"`. Sur 4xx/429, un message français composé à partir du `code` — jamais le `message` du serveur, qui est un diagnostic pydantic — et **aucun** bouton. Même quand la sonde a échoué au chargement : le badge dit « mode indisponible » et la première question affiche le bandeau, plutôt qu'une recherche de mots-clés servie comme si elle avait été vérifiée.
- **Il ne stocke rien de ce qui a été dit** (AD-15) : le `localStorage` ne porte plus que le profil et les préférences d'affichage ; la persistance des conversations héritée du site est retirée, et une conversation déjà enregistrée est réécrite sans elle au premier chargement. Tout texte reçu du serveur est rendu par `textContent`. La mention « où part votre question » vit sous la saisie, dans l'onglet comme dans le panneau flottant.
- **Son badge dit le niveau de validation du corpus servi** (story 1.10) : « mode api · vertical (2 cas) » quand les documents servis portent un gate, « mode api · non validé » quand ils n'en portent pas. `testerApi()` lisait déjà `gate_profile` et `alerts` sur `/sante` et les jetait ; le badge disait « mode api » de la même façon que le corpus soit mesuré ou pas du tout. Le suffixe est composé par une fonction **pure** (`libelleMode(via, validation)`) que `ui.js` se contente de poser dans les deux surfaces ; il ne vaut que pour le mode api, et une sonde illisible ou muette ne suffixe **rien** plutôt que d'annoncer un niveau que personne n'a lu.
- **Il borne son attente** : la requête est abandonnée au-delà de `deadline_s` (lu sur `/sante`) plus une marge, et l'abandon est une indisponibilité comme une autre. Les bornes du contrat viennent du serveur — `historique_max_turns` est lu sur `/sante`, pas recopié —, sauf `Turn.texte`, qui est une contrainte de schéma et qu'un test amarre à `Turn.model_fields`.
- **Il se teste sans navigateur, y compris ce qu'il affiche** : `chat.js` ne compose pas du DOM mais une **description** de ce qu'il faut peindre (`vueReponse`, `vueErreur`, `vueAttente` : un arbre de `{tag, cls, texte, enfants, action, href}`), et `ui.js` n'est plus qu'un matérialiseur sans décision. Les actions sont **décrites** (`{nom: "recherche_simple", question}`), jamais des fermetures : c'est ce qui permet d'affirmer par un test que le bandeau d'indisponibilité porte exactement une action de repli et qu'un 4xx n'en porte aucune — la règle d'AD-16 que rien ne voyait tant que la composition vivait dans le DOM. `tests/js/chat_cases.mjs` charge `chat.js` dans un `node:vm` avec `window`, `location`, `fetch` et les minuteurs doublés ; `tests/test_web_chat.py` asserte les relevés. Aucune dépendance ajoutée. Le rendu final reste vérifié en live (`docs/tests-live.md`).

## Le front du sinistre

`tools/sinistre/` (story 1.9). Une page autonome, sans build, sans framework, sans requête tierce — et **sans** dépendance à `web/app/styles.css` : « style du site » est lu comme sa sobriété (même pile de polices, mêmes cartes arrondies, `color-scheme` clair/sombre), pas comme une feuille de 1 328 lignes taillée pour le DOM du guide, qu'une classe renommée là-bas casserait ici.

- **Elle affiche, elle ne calcule pas** (AD-6 / AD-4) : aucune règle de la table du verdict n'est côté page. `answer.verdict` arrive décidé, avec sa raison composée par le serveur, et la page pose le badge, la portée (« au regard des conditions générales seules — verdict non validé par un expert assurance »), la raison, **les faits compris** (`answer.faits_compris` : bien, événement, lieu, cause, moment — ce que *comprendre* a compris, pas la description en écho), le paquet manquant, les questions à poser, les clauses et la trace dépliable.
- **Les statuts se rattachent par position** : `ClauseSource` ne porte pas de `claim_id` (AD-11 n'en prévoit pas), et la page refait **la même** énumération que `presenter.clauses_de()` — `for claim in answer.claims for quote in claim.quotes` — en vérifiant chaque `block_id`. Au moindre désaccord elle abandonne, **le dit**, et affiche une liste plate : une clause attribuée à la mauvaise affirmation sous un verdict est pire qu'une liste sans rattachement.
- **Les clauses non retrouvées s'affichent sans leur citation** : `answer.rejected_claims` publie tout, y compris des quotes restées les **chaînes du modèle** (`non_retrouvee`, `ambigue`). La page montre le texte de l'affirmation et le motif du rejet en français — la même règle que celle qui les tient hors de `sources[]`.
- **Aucun repli, aucun verdict de remplacement** (AD-16) : sur 400, 429, 503 ou 500, la page affiche l'erreur et sa référence de requête, sans bouton et **sans conserver le verdict précédent** — le conteneur est vidé avant chaque peinture. Un 200 dont le corps n'est pas lisible (pas de `verdict`, pas de `trace`, une clause sans `kind`) est traité comme une panne, pas comme un verdict partiel.
- **AD-15** : avertissement « Démonstrateur public : ne saisissez aucune donnée réelle ou nominative de sinistre » au-dessus du formulaire, mention de confidentialité qui dit ce que la politique du fournisseur dit *réellement* (suppression sous 30 jours, et ses **quatre** réserves — service à rétention plus longue contrôlée par le client, accord de rétention différent, application de la politique d'usage, obligation légale — plus les deux ans du contenu signalé, avec le lien et la date de lecture), rien en `localStorage`, et tout ce qui vient du serveur posé par `textContent`.
- **Elle se teste sans navigateur, composition et peinture** : `sinistre.js` sépare les fonctions pures (`vueVerdict`, `vueErreur`, `vueFormulaire`, `clausesParClaim`, `statutTexte`, `libelleVerdict`, `coutTexte`, `corpsSinistre`) d'un matérialiseur qui ne décide de rien. `tests/js/sinistre_cases.mjs` les charge dans un `node:vm` avec `fetch` et le DOM minimal doublés ; `tests/test_web_sinistre.py` asserte les relevés (88 cas), y compris que les `maxlength` de la page sont **ceux des schémas du serveur** et qu'`innerHTML` ne sert qu'à vider un conteneur. Aucune dépendance ajoutée.

## Infrastructure

`scripts/gcp_bootstrap.sh` (idempotent, `--project=foyer-retour`, `europe-west1`) crée les comptes de service, la fédération d'identité GitHub, le secret, les buckets et le budget ; il affiche les trois variables GitHub à poser (`GCP_PROJECT_ID`, `WIF_PROVIDER`, `DEPLOY_SA`). **Ce que le compte déployeur peut faire, et rien de plus** (resserré en 1.11, sur ce que le premier déploiement réel a effectivement exigé) : au niveau du projet, `run.admin`, `cloudbuild.builds.editor`, `artifactregistry.writer`, `serviceusage.serviceUsageConsumer` et `storage.bucketViewer` (énumérer les buckets, aucun accès aux objets) ; « agir en tant que » **deux comptes nommés** — le runtime `foyer-retour-run@` et le compte de build de Cloud Build —, et non plus tous les comptes du projet ; écrire dans les deux seuls buckets de dépôt de source. La condition du fournisseur d'identité fédérée est comparée à chaque exécution et mise à jour si le dépôt change, au lieu d'être déclarée « déjà présente ». `scripts/hello_world/` est le conteneur minimal qui a validé les rôles sur Cloud Run avant le déploiement automatique ; il était déployé sous le nom final du service, `foyer-retour`, et `deploy.yml` l'a remplacé en place, sans changer d'URL. Le PDF du contrat n'est pas dans le repo : le script le dépose dans `gs://foyer-retour-sources/` depuis `PDF_LOCAL` (chemin fourni à la main).

## Déploiement

Un push sur `main` déclenche `.github/workflows/deploy.yml`, et c'est le seul chemin vers la production. Il n'y a **qu'un** service (`foyer-retour`, `europe-west1`, projet `foyer-retour`) et **qu'une** origine : l'accueil, la copie du site, l'outil sinistre et l'API y vivent ensemble (AD-12).

**Ce que le workflow fait, dans cet ordre :**

1. **Il vérifie d'abord.** Le job `verifier` réutilise `ci.yml` — `ruff check server tests scripts`, puis `ANTHROPIC_API_KEY= FRONT_TESTS_REQUIS=1 uv run pytest -q`. Rien n'est construit tant que ce n'est pas vert, et c'est le même texte que sur une pull request : une seule définition de ce que « vert » veut dire. `node` et `uv` y sont **épinglés** (l'un fait tourner 130 cas de front, l'autre résout `uv.lock`), et un `fetch_source --all` précède `pytest` : sans le PDF du contrat, le seul test qui compare les artefacts AXA committés à ce que le parseur produit aujourd'hui se met en `skip` à la collecte, et la CI qui garde la production jouerait une suite plus faible que celle qu'on annonce.
2. **Il s'authentifie sans clé.** `google-github-actions/auth@v3` échange le jeton OIDC de GitHub contre l'identité du compte de service déployeur, par fédération directe (`permissions: id-token: write`). Aucune clé de compte de service n'existe dans le dépôt ni dans GitHub. Deux choses encadrent cette étape et n'y sont pas par hasard (revue Codex 1.11) : elle est précédée du contrôle des trois variables du dépôt, qui **refuse tout `GCP_PROJECT_ID` autre que `foyer-retour`** — une variable de dépôt s'édite depuis l'interface de GitHub, sans revue et sans diff, et une valeur erronée ferait déployer ailleurs — et de l'installation d'`uv`, un `curl | sh` qui n'a ainsi rien à voler : après `auth`, il tournerait sur un runner portant déjà le crédentiel fédéré du déployeur. Ce crédentiel (`gha-creds-*.json`, écrit dans le répertoire de travail) est exclu de `.gcloudignore`, `.dockerignore` et `.gitignore` : sans quoi il partirait dans le bucket de sources avec l'archive de `--source`. Et la frontière véritable est côté GCP : la condition du fournisseur d'identité fédérée borne le dépôt **et** `assertion.ref == "refs/heads/main"` — le `if:` d'un workflow ne dit rien à IAM.
3. **Il construit et déploie sans trafic.** `deploy-cloudrun@v3` avec `--source` : Cloud Build construit l'image (le PDF du contrat n'est pas dans le dépôt — `fetch_source --all` le télécharge au build, empreinte vérifiée, repli sur `gs://foyer-retour-sources/`), et la révision part **sans trafic**, sous le tag `candidat`. Le secret est monté à une **version épinglée** (`ANTHROPIC_API_KEY=ANTHROPIC_API_KEY:1`), et `GIT_SHA` porte le `sha7` du commit.
4. **Il sonde la révision candidate**, sur son URL taguée (`https://candidat---…`) et non sur celle du service — c'est ce que `deploy-cloudrun@v3` publie en sortie `url` dès que l'entrée `tag` est posée, et le workflow confronte cette sortie à l'URL qu'il relit sur `status.traffic[]` avant de sonder quoi que ce soit : `uv run python scripts/smoke.py --base-url … --version <sha7>` joue **quatre vérifications** —
   - `GET /api/v1/sante` : les deux documents servis, le `gate_profile` **et** le nombre de cas du manifest de ce commit, `version` = le `sha7` déployé, les seuils dont le smoke tire sa patience, et **aucune** alerte (une dérogation `ALLOW_UNGATED` posée à la main sur le service se voit ici) ;
   - les trois surfaces d'AD-12 — `/`, `/guide/`, `/sinistre/` — répondent 200 : un `COPY web` disparu du `Dockerfile` ou un montage statique cassé donnerait sinon une API parfaite devant trois pages mortes ;
   - `POST /api/v1/chat` : le cas témoin du guide, rejoué par HTTP — `via`, la réponse trouvée, au moins une claim `retrouvee`, l'empreinte de source du manifest ;
   - `POST /api/v1/sinistre` : le cas de la bougie, plus le verdict, qui doit tomber dans les valeurs admissibles écrites dans le cas.

   Les deux premières ne coûtent rien, les deux dernières appellent un modèle : **l'ordre est voulu**, un déploiement déjà refusé n'a pas à être confirmé à 0,08 €.
5. **Il promeut le trafic seulement ensuite, et vers la révision qu'il vient de sonder** : `update-traffic --to-revisions=<la révision taguée>=100 --remove-tags=candidat`. Nommer la révision plutôt que `--to-latest` n'est pas un détail : « la dernière créée » n'est pas forcément celle que le smoke a validée, et un déploiement lancé à la main pendant les quarante secondes du smoke recevrait sinon 100 % du trafic sans avoir jamais été vérifié.
6. **Si quoi que ce soit échoue, il retire le tag.** Un smoke rouge fait échouer le workflow **avant** la promotion, et la révision précédente garde 100 % du trafic ; mais la révision refusée resterait joignable sur `https://candidat---…` — publiquement, `--allow-unauthenticated` valant aussi pour l'URL taguée, et avec le secret Anthropic monté. Une étape `if: failure() || cancelled()` la détague — une annulation à la main, ou le plafond `timeout-minutes`, laisse exactement la même révision en vol qu'un échec. Il n'existe aucun chemin qui promeuve « quand même » (AD-16).

**Retour arrière.** Une révision servie qui se révèle mauvaise se retire sans rien reconstruire :

```bash
gcloud run revisions list --service=foyer-retour --region=europe-west1 --project=foyer-retour
gcloud run services update-traffic foyer-retour --to-revisions=<révision-précédente>=100 \
  --region=europe-west1 --project=foyer-retour
```

**Dimensionnement (AD-13), et la règle qui le protège.** Le service tourne en `--allow-unauthenticated --max-instances=1 --concurrency=2 --timeout=60 --min-instances=0`. `deploy.yml` en est l'**autorité** — c'est le seul endroit qui les *décide* ; ce paragraphe et `docs/tests-live.md` ne font que les citer, et un test relit le workflow pour que la citation ne prenne jamais le pas sur la source. Ce sont des drapeaux d'infrastructure, pas des seuils de `config.py` (qui configure le processus). `--max-instances=1` est le **plafond dur** de la facture, avec le plafond de coût par requête et le plafond fournisseur. **Le passage à `--max-instances=2 --concurrency=8` n'aura lieu qu'après un test mémoire/latence** — deux requêtes de pipeline concurrentes dans 512 Mio avec PyMuPDF chargé n'est pas une hypothèse qu'on pose en écrivant un chiffre.

**Relancer un déploiement à la main.** `deploy.yml` accepte `workflow_dispatch`, mais le job de déploiement porte `if: github.ref == 'refs/heads/main'` : le bouton de GitHub laisse choisir la branche, et sans cette garde un « Run workflow » sur une branche de travail aurait construit et promu ce code en production. Sur une autre référence, le lint et la suite tournent et rien n'est déployé.

**Ce dont le workflow a besoin, et qui se pose une fois** : les trois variables du dépôt affichées par `scripts/gcp_bootstrap.sh` — `GCP_PROJECT_ID`, `WIF_PROVIDER`, `DEPLOY_SA` (`gh variable set …`). Le workflow refuse de démarrer si l'une manque, plutôt que d'échouer au milieu d'un build facturé.

**Ce que le déploiement automatique ne fait pas** (NFR13, et c'est écrit plutôt que sous-entendu) : ni Cloud Armor, ni load balancer, ni domaine personnalisé, ni SLO, ni supervision, ni test de charge, ni évals en intégration continue (le sous-ensemble rapide vient en 4.1). Le limiteur reste best-effort par instance.

## Principes

- **Restitution d'abord** : source par affirmation, état explicite (sûr / partiel / inconnu), trace consultable par réponse, coût affiché.
- **Déterminisme sur les vrais invariants** : le modèle propose, le code vérifie ; pas de verdict sans clause citée et retrouvée mot pour mot dans la source.
- **L'intelligence se paie une fois, à l'ingestion** ; la requête reste légère.
- **Un document mal ingéré n'est pas servi** : rapport d'ingestion visible, quarantaine.
- **Écrit pour être relu** : petits commits qui disent pourquoi, README pour le mainteneur qui arrive.
