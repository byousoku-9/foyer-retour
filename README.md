# foyer-retour

Un retour à trois problématiques partagées par l'équipe IA de Foyer — un chatbot pour les nouveaux arrivants au Luxembourg, un sinistre confronté aux conditions générales d'une assurance habitation, un « RAG » sur un Excel de cent mille lignes — prouvé par deux prototypes déployés et une réponse d'architecture pour le troisième.

Le fil rouge : **on ne gagne pas sur « comment on retrouve », on gagne sur « comment on prouve ».** Chaque affirmation montrée à l'utilisateur a survécu à une vérification par du code ; ce que le système ne sait pas est dit, avec la preuve.

## État — ce que le produit fait aujourd'hui

**Les deux prototypes sont livrés et déployés ; le troisième sujet a sa réponse d'architecture.**

- **L'assistant du guide** (`/guide/`) répond aux questions d'un nouvel arrivant au Luxembourg à
  partir des 36 fiches et 41 questions fréquentes de « S'installer au Luxembourg ». Chaque phrase
  affichée cite le passage qui la soutient ; ce qui n'est pas soutenu n'est pas montré. Il répond en
  **français, anglais, allemand et portugais** — les citations, elles, restent en français mot pour
  mot. Il tient une conversation, exploite le profil déclaré, et dit « je ne sais pas » avec la
  preuve de ce qu'il a cherché.
- **L'outil sinistre** (`/sinistre/`) confronte un sinistre décrit en clair aux **conditions
  générales réelles** de deux contrats habitation luxembourgeois (AXA OptiHome 2017, Baloise Home
  2024). Il rend un verdict conservateur « au regard des conditions générales seules », les clauses
  qui le portent avec leur type et leur page, ce qui manque pour trancher, et les questions à poser.
  Cliquer sur une clause ouvre la page du PDF, surlignée. Le verdict est calculé par du **code pur**
  (`server/app/domain/verdict.py`) : le modèle extrait, le code décide.
- **Le sujet 3 — le « RAG » sur cent mille lignes d'Excel** — n'est pas implémenté, et la page
  d'accueil ne prétend pas le contraire : il reçoit une réponse d'architecture écrite, pas une
  démonstration.

**Trois documents sont servis** — le guide et les deux contrats —, chacun avec son gate de
questions-témoins, son rapport d'ingestion consultable et ses alertes publiées sur
`GET /api/v1/sante`. Le niveau de validation affiché sur l'accueil est **lu sur l'API**, jamais
écrit en dur : `vertical`, et la contresignature humaine des cas reste due — la page le dit.

**Épics livrées :** 1 (les cinq étapes, le serveur, le déploiement automatique), 2 (dictionnaire,
conversation, profil, multilingue, « Pourquoi cette réponse », navigation par outils), 3 (ingestion
PDF générique, typage des clauses, renvois et définitions par portée, pages surlignées, second
contrat, sinistre conversationnel), 4 (harness de questions-témoins, holdout scellé, baselines
publiées, gate `full`), 5.1 à 5.3 (accueil, `docs/architecture.md`, `docs/choix-et-limites.md`).
Le détail story par story, avec ses preuves, est dans `docs/tests-live.md` et
`_bmad-output/` — hors de ce dépôt public.

**Ce qui reste ouvert est écrit, pas tu :** `docs/choix-et-limites.md` porte les limites assumées et
les dettes mesurées, et l'accueil publie l'état de validation réel plutôt qu'un état souhaité.

Le correctif Story 4.5 remplace ce dernier arbitrage historique : `rediger_max_tokens=2048` est
maintenant l'unique plafond de rédaction du guide, pour `outils` comme pour `deterministe`, sous le
plafond courant de **3,50 € par requête** (`max_cost_eur_per_request`). Ce plafond a été relevé
trois fois pour la même raison, qui n'est pas une dérive : le sommaire entier du document vit dans le
préfixe cacheable, et le chemin servi l'y **écrit** au premier tour de navigation. Une requête
sinistre nominale coûte ≈ 0,67 € à froid contre 0,199 € à chaud (mesures du 03/09/2026 dans
`docs/tests-live.md` et `config.py`) ; le plafond couvre le pire chemin nominal froid des douze
appels d'AD-1 avec 12 % de marge, et reste 2,8 fois sous le régime où aucun préfixe n'est relu. Il
n'est cité ici que depuis `config.py`, et un test l'y amarre.

## Lancer

```bash
uv sync                                   # Python 3.13 et dépendances épinglées (pyproject.toml, uv.lock)
cp .env.example .env                      # puis renseigner ANTHROPIC_API_KEY (jamais commité)
uv run python -m server.app.llm.models --check   # vérifie que les IDs de modèles existent (exit 2 sans clé)
uv run uvicorn server.app.api.main:app --port 8787 --proxy-headers --forwarded-allow-ips='*'
```

Puis <http://localhost:8787/> : l'accueil (les trois entrées, la réponse au sujet 3, le niveau de validation lu sur l'API), le guide sous `/guide/`, l'outil sinistre sous `/sinistre/`, l'API sous `/api/v1/`.

```bash
curl -s localhost:8787/api/v1/sante | python3 -m json.tool
curl -s -X POST localhost:8787/api/v1/chat -H 'X-Forwarded-For: 203.0.113.7' \
     -H 'content-type: application/json' \
     -d '{"question":"Quel délai pour déclarer mon arrivée ?","profil":{},"historique":[]}'
```

`--proxy-headers --forwarded-allow-ips='*'` dit à uvicorn de croire le proxy sur le schéma et l'adresse d'origine : c'est ce qui garde les redirections de `/guide` en `https` derrière Cloud Run. Le limiteur, lui, n'en dépend pas — il lit l'en-tête `X-Forwarded-For` directement, comme AD-13 le demande. En `ENV=dev` l'en-tête est facultatif (identité `local`) ; en production, une requête de pipeline qui n'en porte pas est refusée en 400.

## Tester

```bash
uv run ruff check server tests scripts    # lint (ruff épinglé dans le groupe dev, règles dans pyproject.toml)
ANTHROPIC_API_KEY= uv run pytest -q       # unitaires, sans réseau : les appels modèle sont rejoués depuis tests/llm_fixtures/
uv run pytest -q                          # avec la clé, les tests qui appellent un modèle ré-enregistrent leur fixture
```

Ce sont les deux commandes de l'intégration continue (`.github/workflows/ci.yml`), qui pose aussi `FRONT_TESTS_REQUIS=1`. Elle a deux niveaux explicites. Sur une pull request, la suite reste **hermétique** : aucun jeton GCP, aucun téléchargement privé, et les tests qui demandent les PDF réels sont donc absents par `skip` plutôt que maquillés en preuve. Avant un déploiement de `main`, le même workflow est appelé avec `sources_reelles: true` : il fédère le compte lecteur, exécute `uv run python -m server.ingest.fetch_source --all --private-source` directement contre le bucket privé, puis joue nommément les deux tests de régénération avec `REAL_PDF_TESTS_REQUIRED=1` avant la suite. Localement, obtenir la même preuve forte demande ce mode privé avec un access token de lecture. Hors de cette porte, le chemin normal reste public : toute `HTTPError` déclenche son unique repli GCS, et seul un HTTP 406 provoque auparavant une seconde négociation publique bornée.

- **Les tests du front demandent `node`** (`tests/test_web_chat.py` exécute `tests/js/chat_cases.mjs`, `tests/js/ui_cases.mjs` et `tests/js/corps_servi.mjs` ; `tests/test_web_sinistre.py` exécute `tests/js/sinistre_cases.mjs` ; `tests/test_web_accueil.py` exécute `tests/js/accueil_cases.mjs` — tous dans un `node:vm`). Sans lui, ces cas passent en `skip` — et un `skip` ne se distingue pas d'un succès dans un `pytest -q`. Poser `FRONT_TESTS_REQUIS=1` transforme le skip en échec ; la CI la pose (`ci.yml`), pour qu'une image sans `node` ne puisse pas faire passer la suite au vert en taisant la moitié du front.
- `tests/test_layers.py` vérifie statiquement les couches du spine (`domain` n'importe rien ; une étape n'importe jamais une autre étape).
- `tests/test_domain.py` vérifie que chaque modèle porte exactement les champs et enums de son AD.
- `tests/test_api_sinistre.py` joue la matrice HTTP des trois routes du sinistre avec un pipeline **doublé** : le contrat de sortie, les deux refus en 400 avant tout appel facturé, le 429 et son `Retry-After`, les 503 avec leur trace partielle, et le 500 d'une clause que le corpus ne confirme pas.
- `tests/test_evals_run.py` joue la matrice du runner de questions-témoins avec un pipeline **doublé** et un corpus miniature : la validation stricte des cas, les sept labels et leur précédence, les quatre codes de sortie, l'écriture du gate et ce qui ne doit **pas** toucher le manifest. Aucun réseau.
- `tests/test_langues_live.py` rejoue six questions réelles (deux EN, deux DE, deux PT) et leur contrôle `micro` par retraduction ; les fixtures gardent ce contrôle hors réseau dans la suite ordinaire.
- `tests/test_verdict.py` joue la table d'AD-6 **sans modèle ni corpus** : c'est la propriété que le découpage « le modèle extrait, le code décide » cherchait, et un cas de `tests/test_layers.py` interdit à `domain/verdict.py` d'importer `corpus`, `llm` ou `steps`.
- Les seuils numériques vivent dans `server/app/config.py` et se surchargent par variable d'environnement.
- Ré-enregistrer une fixture LLM : supprimer `tests/llm_fixtures/{module}.{test}.json` puis relancer ce test avec `ANTHROPIC_API_KEY` renseignée (réseau, coût) ; committer le JSON avec le pourquoi.
- Les vérifications qui touchent le réseau (GCP, API) sont consignées dans `docs/tests-live.md`.
- **Un commit, une raison.** Avant de pousser, relire `git log --oneline` de la story : un commit dont le titre dit « et au passage » en porte deux, et la convention Git du spine n'en veut qu'une. Le cas s'est produit en 1.11 — `0c1ff74` changeait le mécanisme de version Cloud Run *et* corrigeait un seuil périmé dans `.env.example` —, et il n'était plus réparable : ce commit précédait celui qui a été déployé et que `docs/tests-live.md` cite, réécrire l'historique aurait rendu le relevé live impossible à recouper. La règle se tient **avant** le commit, jamais après (reprise différée 1.11).

## Questions-témoins et gate de service

Le golden set vit dans `server/evals/cases/{guide,sinistre,parsing}/`, au schéma d'AD-14 (`id`, `suite`, `profile`, `question`, `expected`, `truth`, `mode_attendu`). Le runner exécute les pipelines réels pour guide/sinistre et la comparaison locale pour parsing, attribue exactement un des sept labels et écrit à chaque run un JSON détaillé ainsi qu'une table Markdown. Le mode d'emploi complet (cache, CI, profils et arrêt budgétaire) est dans [`docs/evals/harness.md`](docs/evals/harness.md).

```bash
# Les évals refusent de tourner sans clé (AD-14) : les unitaires passent sans, les évals non.
uv run python -m server.evals.run --suite guide          # exécute la suite, un cas par ligne
uv run python -m server.evals.run --case s-bougie-canape # un seul cas
uv run python -m server.evals.run --profile full --quick --max-cost 1.0
uv run python -m server.evals.run --gate lux-guide --profile vertical              # écrit le gate
uv run python -m server.evals.run --gate axa-lu-optihome-2017 --profile vertical
```

Codes de sortie, et ce qu'ils font au manifest :

| code | situation | `data/manifest.json` |
|---|---|---|
| 0 | tous les cas `ok` | gate écrit `evals_ok: true` (avec `--gate`) |
| 1 | un cas rend un mauvais label, ou laisse une attente inassouvie | **avec `--gate`** : gate écrit `evals_ok: false`, le document part en `gate_echoue` au prochain démarrage. Sans `--gate` : rien n'est écrit |
| 2 | refus : pas de clé, profil ou suite non livrés, cas invalide, document non servi | **non modifié** |
| 3 | incident : `Timeout`, `LlmUnavailable`, `BudgetExceeded`, plafond de run atteint | **non modifié** |

La ligne de partage entre 1 et 3 est celle d'AD-8 : un mauvais label est un **résultat**, et le gate est fait pour le consigner ; un incident réseau ne dit rien du système mesuré, et le laisser retirer un document du service serait une panne inventée.

- **`manifest.gate` n'est écrit que par ce runner** (AD-7). L'ingestion ne l'écrit jamais : elle le conserve seulement quand les nouveaux `document_hash` et `overlay_hash` sont byte-identiques aux précédents, sinon elle le met à `null`. Le gate porte le `source_hash`, l'`ingest_fingerprint` et l'`overlay_hash` **de l'entrée du manifest** : les recalculer donnerait un gate qui se valide lui-même.
- **Un document est servi ssi aucun bloquant statique et (`gate.evals_ok` ou `ENV=dev` ou `ALLOW_UNGATED`)** (AD-8). Les deux moitiés sont appliquées par le loader : il relit `report.json` pour le seul niveau `bloquant`, et compare le gate à l'entrée. Un rapport absent ou illisible n'est **pas** un bloquant (AD-8 en fait un artefact d'ingestion ; l'illisibilité est dite par l'alerte `rapport_illisible` de `/sante`).
- **`ALLOW_UNGATED` est fermé en production** : le `Dockerfile` ne l'arme plus, et en `prod` `config.py` force `allow_ungated=False` — poser `ALLOW_UNGATED=true` sur le service ne l'arme pas (AC 1.10). Le refus n'est pas muet : l'alerte `ungated_refuse_en_production` paraît sur `/api/v1/sante` et un avertissement part au journal de démarrage. La dérogation ne vaut plus qu'en `ENV=dev` ; en production, un gate invalidé se répare en relançant les témoins (`--gate`).
- **Le plafond de coût est par run**, pas par requête (AD-9) : `evals_max_cost_eur` dans `config.py`, surchargeable par `--max-cost`. Le runner s'arrête **avant** l'appel qui le dépasserait, conserve les cas terminés et écrit des rapports `complete=false`, sans toucher au manifest.
- **Un gate que le schéma ne sait plus lire se reprend aussi.** Quand `Gate` gagne un champ obligatoire, tous les gates déjà écrits deviennent des entrées de manifest invalides : leur document part en quarantaine, et `--gate` refuserait « document non servi » — le blocage même que la reprise d'un gate rouge évite, par une autre porte. Pour le seul document visé, et en lecture seulement, un gate que l'image ne sait pas lire est donc traité comme absent ; à l'écriture, les autres entrées sont recopiées telles quelles, leur gate périmé compris, et leur propre `--gate` le refera.
- **Un gate rouge se reprend.** Un run qui écrit `evals_ok: false` met le document en quarantaine `gate_echoue` (AD-8 : « jamais servi »). Le runner sait malgré tout le re-mesurer : `--gate {doc_id}` lit alors un manifest **de lecture** où le seul gate de ce document vaut `null` (vue temporaire confinée, avec répertoires réels et fichiers liés physiquement ou copiés en repli ; `data/` n'est pas touché). Un verdict d'éval ne doit pas rendre l'éval impossible. Tout le reste d'AD-7 continue de s'appliquer : hashes, overlay, bloquant statique, `status: quarantaine`.
- **Quand faut-il relancer les gates ?** Dès que `pipeline_digest`, `prompts_digest` ou `model_ids` bougent — c'est-à-dire dès qu'on touche l'une des cinq couches `server/app/{steps,pipelines,corpus,domain,llm}/` ou un prompt. Toutes cinq entrent dans l'empreinte : leurs règles, schémas et propriétés gouvernent ensemble ce que le loader sert et ce que le pipeline rend. L'extension de la définition à `domain` pendant la story 3.5 n'attribue donc pas à cette seule couche les changements de digest de la campagne : chaque hash décrit l'instantané complet de ces cinq couches. Un gate plus ancien produit l'alerte `gate_perime` ; `tests/test_digests.py::test_les_gates_du_depot_sont_ceux_de_limage_courante` rougit dans ce cas et donne la commande. Deux runs coûtent environ 0,10 € et demandent la clé.
- **Tout l'epic 4 est livré.** Le profil `full`, le sous-ensemble `--quick`, les variantes compatibles et le cache persistant viennent de 4.1 ; la suite `parsing` locale et `docs/evals/latest.md` de 4.2 ; le **holdout scellé** de 4.3, les **baselines publiées même quand elles contredisent** de 4.4, et le **gate `full`** avec `GET /api/v1/evals/latest` de 4.5. Cette ligne annonçait encore ces trois derniers comme non livrés : c'était faux, et la section « État » en tête du fichier disait déjà le contraire.
- **`server/evals/` n'est jamais importé par `server/app/`** (`tests/test_layers.py` le vérifie statiquement) : le système mesuré ne dépend pas de ce qui le mesure. Le runner construit corpus, index et client exactement comme `api/etat.py` le fait pour les routes.
- **`pyyaml` est une dépendance de développement seule** : l'image est construite avec `uv sync --frozen --no-dev` et ne la reçoit pas.

## L'accueil

`tools/accueil/` (story 1.10). Servi sur `/` par le montage statique ; vanilla, sans build, sans framework, sans requête tierce, sans `localStorage`.

- **Trois entrées** (`/guide/`, `/sinistre/`, le sujet 3), **la réponse écrite au sujet 3** — « je ne fais pas un RAG » : la table va dans une base SQL, on filtre d'abord, le modèle traduit la question en requête (schéma + échantillon de valeurs, requête **affichée**, lecture seule, `LIMIT`, timeout) et ne calcule rien, le texte libre n'est cherché qu'**après** le filtre et sur les colonnes de texte, un profil par colonne est calculé à l'ingestion, et la restitution montre la requête, le nombre de lignes, les lignes sources et ce que les données ne disent pas — et les liens vers le dépôt.
- **Le niveau de validation est lu, jamais écrit** : `accueil.js` sonde `GET /api/v1/sante` et compose une phrase depuis `gate_profile`, `gate_cases` et `gate_countersigned`. « 2 cas » n'est écrit nulle part dans la page — un test le vérifie en servant un gate à un cas et en attendant « 1 cas relu ».
- **« Relus à la main » n'est écrit que si une main les a relus.** AD-14 définit `vertical` par une relecture humaine, et la page l'affirme publiquement : la qualification vient donc de `gate_countersigned`, pas du nom du profil. Tant que la contresignature est due, la page écrit « N cas relus par la boucle, contresignature humaine en attente » et le badge du guide porte « non contresigné ». Pour la lever : remplir `truth.countersigned_by` (nom + date) dans les deux YAML et relancer les deux `--gate` — `cases_hash` change.
- **Trois états, et trois seulement** : la sonde répond avec un profil (« niveau de validation : vertical — N cas », qualifié « relus par la boucle, contresignature humaine en attente » tant que `gate_countersigned` est faux et « relus à la main » une fois la contresignature portée dans les cas — c'est l'état d'attente qui est celui du dépôt aujourd'hui —, plus les alertes) ; elle répond sans profil (« aucun gate » + pourquoi) ; elle ne répond pas (« inconnu — le serveur n'a pas répondu »). Le troisième n'affiche **jamais** le dernier profil connu ni un défaut optimiste. Un 200 que la route n'aurait pas pu écrire — clé absente, `gate_profile` sans `gate_cases` ou sans `gate_countersigned` — est traité comme une sonde en échec, pas comme un niveau à moitié lu.
- **Elle se teste sans navigateur** : composition pure (`lireSante`, `libelleValidation`, `vueEtat`, `vueAlertes`, `vueSondeEchouee`) et matérialiseur `textContent` sans décision ; `tests/js/accueil_cases.mjs` dans un `node:vm`, `tests/test_web_accueil.py` pour les assertions.

## Ingestion du guide

```bash
uv run python -m server.ingest.kb_to_blocks        # data/lux-guide/source.js → document.json, summary.md, report.json ; fusion de data/manifest.json
```

- `data/lux-guide/source.js` est la copie octet-identique de `web/app/kb.js` (filiation dans `data/lux-guide/README.md`) ; le parseur est en Python pur, sans Node.
- Sortie déterministe : relancer ne modifie rien ; `document.json` ne contient jamais `text_norm`, recalculé au chargement.
- Exit 1 et `status: quarantaine` dans `manifest.json` si un check bloquant (invariant d'arbre) est levé ; `ids_disparus` est une alerte calculée contre le `document.json` précédent.
- `manifest.gate` reste `null` jusqu'au premier gate des questions-témoins (story 1.10) ; en dev, `ALLOW_UNGATED` sert le document avec l'alerte `sans_gate`.
- Le serveur lit `data/` par `server/app/corpus/loader.py` (hashes recalculés, quarantaine par document) et l'indexe par `server/app/corpus/index.py` ; les seuils (`search_limit`, `node_window`) viennent de `server/app/config.py`.

## Dictionnaire enrichi

`data/dictionary.json` donne à *retrouver* les **variantes** d'un terme (français familier, anglais, allemand, portugais) et arme, une fois validé à la main, le refus « zéro hit » d'AD-5. Il est écrit par l'ingestion, lu par le serveur au démarrage, et committé (AD-7).

```bash
uv run python -m server.ingest.enrich_dictionary --dry-run        # le plan des requêtes et le majorant de coût, rien d'écrit
uv run python -m server.ingest.enrich_dictionary                  # écrit data/dictionary.json, validated: false
uv run python -m server.ingest.enrich_dictionary --valider "Nom"  # la signature humaine, et la seule chose qui arme le refus
```

- **Une requête par unité documentaire**, plus une pour les déclencheurs d'intention. Le guide conserve byte-identiques ses catégories et fiches historiques. Un contrat utilise uniquement ses blocs citables rattachés à leur vrai nœud : groupes bornés par `dictionary_flat_max_blocks_per_request` et `dictionary_flat_max_input_chars`, texte exact (préfixe explicitement signalé si un bloc dépasse seul la borne), aucune fiche ni hiérarchie inventée. Le majorant du run entier est calculé avant tout appel. Le défaut historique reste Batch ; en développement, `--transport standard` part de zéro via `messages.create`, sans Batch, remise ni retry, et chiffre le coût réel depuis l'usage standard.
- **Le code ne fait pas confiance au modèle** (AD-5 / AD-7 / FR29 : il ne renvoie jamais de texte de bloc). Chaque chaîne rendue passe les bornes de `config.py` (`dictionary_term_max_chars`, `dictionary_term_max_words`, `dictionary_question_max_chars`, …) et le contrôle « chaîne recopiée d'un bloc » ; hors borne, elle est **écartée, jamais tronquée**, et le compte des écarts est affiché en fin de run. Un `fiche_id` que la catégorie ne contient pas est écarté de même.
- **Deux verrous distincts, publiés par `/api/v1/sante` et affichés sur `/`** : `corpus_ok` (les `corpus_source_hashes` du fichier décrivent le corpus servi) commande l'emploi des **variantes** par *retrouver* ; `validated ∧ corpus_ok` — c'est `refus_zero_hit_actif` — commande le **court-circuit** d'AD-5. Élargir la recherche n'affirme rien et chaque phrase affichée reste vérifiée contre le corpus (AD-3) ; **refuser** est une affirmation négative, visible et irréversible pour celui qui la reçoit : c'est elle que la signature humaine garde.
- **Ce que la non-validation désarme, et rien d'autre** : le court-circuit « zéro hit » **avant** *retrouver*. Le refus par intent reste actif, les variantes servent, et une question sans aucun hit est refusée quand même — par le garde-fou « zéro bloc » de la story 1.5, avec la même preuve. Ce qui distingue les deux est observable : la présence de l'étape `retrouver` dans la trace.
- **`--valider "Nom"` écrit trois champs et ne touche à aucun autre** (`validated`, `validated_by`, `validated_at` en UTC ISO 8601), et refuse (exit 5) si le fichier ne décrit plus le corpus livré. C'est un commit `data` dédié. Rien dans l'ingestion n'écrit jamais `validated: true`.
- Un dictionnaire absent, illisible, non conforme ou d'un autre corpus **désactive une optimisation, il n'empêche jamais de servir** et ne lève jamais au démarrage (AD-7) ; il est **dit** — alertes `dictionnaire_non_valide` / `dictionnaire_corpus_perime` sur `/api/v1/sante`, ligne « dictionnaire des variantes » sur l'accueil, `CheckResult(dictionnaire)` dans la trace de *retrouver* (AD-16 : aucun dégradé silencieux).
- **`intents` et `candidate_questions` sont produits, versionnés — et lus par personne**, délibérément (`target_story: 2.5`). AD-5 est explicite : « les déclencheurs d'intention sont distincts des mots du corpus — la présence d'un mot n'est jamais une preuve de pertinence » ; refuser une question parce qu'elle contient « météo » ferait exactement ce que cette phrase interdit, et le refus par `intent`, décidé par *comprendre* qui a lu la question entière, est déjà en place et suffit. Les deux champs existent pour servir de **mesure** en 2.5 (« pourquoi cette réponse ») : confronter l'`intent` rendu aux déclencheurs pour dire quand les deux divergent, sans jamais laisser les seconds trancher ; et proposer des questions candidates, qui est une décision d'interface.
- Les consignes d'ingestion vivent sous `server/ingest/prompts/` et **non** sous `server/app/llm/prompts/` : y entrer les mettrait dans `prompts_digest`, et modifier une consigne d'ingestion rendrait les gates `gate_perime` pour un prompt que le serveur n'exécute jamais.
- Le périmètre annoncé à *comprendre* (`Corpus.perimetres`) est une projection des titres du corpus, calculée au chargement et bornée par `perimetre_max_chars` : une fiche ajoutée entre dans le périmètre sans qu'on réécrive une phrase de prompt.

## Ajouter un contrat PDF

```bash
# 1. Créer data/<doc-id>/source.url et source.sha256 depuis la source publique et son hash vérifié.
# 2. Télécharger le PDF local (il est ignoré par Git).
uv run python -m server.ingest.fetch_source <doc-id>

# 3. Produire puis vérifier la structure Opus hors ligne (Messages standard, jamais Batch).
uv run python -m server.ingest.structure <doc-id> --max-cost <euros> --dry-run
uv run python -m server.ingest.structure <doc-id> --max-cost <euros>

# 4. Réingérer avec cette structure et les métadonnées imprimées, puis relire report.json.
uv run python -m server.ingest.pdf_to_blocks <doc-id> --title "Titre imprimé" --edition "Édition imprimée"

# 5. En développement, voir d'abord le plan puis partir de zéro via Messages standard.
#    Le même plafond explicite est obligatoire sur les deux commandes ; aucun endpoint Batch.
uv run python -m server.ingest.type_clauses <doc-id> --transport standard --max-cost <euros> --dry-run
uv run python -m server.ingest.type_clauses <doc-id> --transport standard --max-cost <euros>

# 6. Générer le vocabulaire du contrat depuis ses vrais blocs, en standard en développement.
ANTHROPIC_API_KEY= uv run python -m server.ingest.enrich_dictionary --doc-id <doc-id> \
  --transport standard --max-cost 10 --dry-run
uv run python -m server.ingest.enrich_dictionary --doc-id <doc-id> \
  --transport standard --max-cost 10

# 7. Après l'état final, certifier ce document avec ses empreintes et digest courants.
uv run python -m server.evals.run --gate <doc-id> --profile vertical
```

- Le PDF n'est **jamais committé**. `fetch_source` vérifie `source.sha256`, accepte une URL `https://` ou `gs://`, et le build rejette tout hash divergent. Sur un 406 public seulement, il renégocie une fois la même URL comme téléchargement navigateur complet (`Range: bytes=0-`); une plage partielle ou un contenu changé échoue toujours au SHA et n'est jamais écrit. `source.url` est recopié dans `Document.source_url`; titre et édition restent des entrées explicites, car les deviner fabriquerait une valeur éditoriale.
- `pdf_to_blocks` conserve texte, page, coordonnées et lignes ; regroupe chaque grille détectée dans un bloc `table` atomique (`cellule | cellule`) ; marque couverture et TdM comme `autre`; compare la TdM imprimée à l'arbre et les signets PDF dans un contrôle séparé. Les blocs préliminaires restent inspectables mais ne consomment pas le budget de rappel.
- L'OCR est **ciblé** : seulement une page visuelle sans couche texte, avec Tesseract et les données françaises (`fra.traineddata`). Un succès produit des blocs `source_field=ocr`; moteur absent ou sortie vide laisse `page_sans_texte` bloquant et nomme la dépendance. Un logo sous la densité configurée ne suffit pas à signaler une page mixte.
- `report.json` est à relire avant tout gate. Une page non blanche encore sans texte, un invariant d'arbre ou une page de charabia portant un kind juridique met le document en quarantaine. Numérotation, TdM, densité mixte, résidus, langue, références, définitions, marqueur d'exclusion, confiance et kinds non confirmés alertent ; la couverture globale reste toujours informative.
- `type_clauses` envoie le texte au modèle seulement comme entrée non fiable et exige une sortie `extra="forbid"` sans extrait. Le registre T1 content-addressé est gelé avant la planification ; T2 relit indépendamment les kinds juridiques et, en mode `ISOLATED`, chaque `renvoi` modèle sans élargir `LEGAL_KINDS`. Un désaccord critique déclenche une troisième lecture Sonnet/Opus d’ingestion bornée. La décision terminale est l’unique autorité : hors `CONFIRMED`, portée, référence, décision, citation et verdict restent sans effet. L’ancien `typing.manual.json` est inactif et n’est jamais restauré.
- `run()` et le CLI gardent **Batch par défaut uniquement pour une procédure de production explicitement autorisée**. En développement, toujours fournir `--transport standard` : T1, T2 et l’arbitre passent par `messages.create`, sans appel à `messages.batches`, avec concurrence, retries 429/5xx et plafond réservé avant chaque appel. Les lots sont agrégés par `custom_id`, leur coût vient de l'usage API avec la remise Batch ; le standard utilise le tarif sans remise. Dans les deux voies, une réponse absente, tronquée ou hors schéma devient une décision terminale sans effet pour les identités concernées. Une reprise byte-identique préserve le gate ; un changement du document l’invalide. `typing.manual.json` n’est ni une entrée active ni une voie de restauration.
- Les variantes du guide restent dans `data/dictionary.json`. Celles d'un contrat vivent dans `data/<doc-id>/dictionary.json` et se génèrent en développement avec `--doc-id <doc-id> --transport standard --max-cost <euros>` après un dry-run au même plafond. Le serveur charge chaque dictionnaire une seule fois et ne transmet au pipeline que celui du contrat interrogé. Le dictionnaire Baloise versionné est la sortie reproductible de 35 unités de blocs réels + les intents : la campagne standard du 27/08/2026 a exécuté 36 appels sans retry ni Batch, pour **2,8518 EUR** réels sous un majorant de **5,0002 EUR**, et produit 540 canoniques, 3 029 variantes et 87 déclencheurs. Il reste `validated=false` jusqu'à la validation humaine distincte.
- Les `custom_id` lient cryptographiquement chaque nouveau lot à la projection structurelle et textuelle complète, aux prompts, au modèle, aux schémas exacts, aux seuils et à l'implémentation. Le dry-run affiche cette empreinte. Les lots historiques antérieurs à ce lien ne sont repris qu'avec leurs deux IDs **et** `--legacy-resume <empreinte-campagne>` ; cette voie ne soumet rien et refuse toute empreinte différente. Un verrou OS exclusif empêche deux typages d'écrire le même document en concurrence.
- Tous les seuils d'ingestion vivent dans `server/app/config.py`, sont publiés par `thresholds()` et entrent dans `ingest_fingerprint` lorsqu'ils changent extraction ou segmentation.
- `tests/test_parsing_axa.py` compare les pages 9, 11, 34 et 46 à des extraits relus (`tests/data/axa/`) contre le `document.json` committé ; si `source.pdf` est présent, l'ingestion PDF doit regénérer à l'identique le texte, les lignes, les coordonnées, l'ordre et les IDs. Le typage Batch enrichit ensuite les kinds, relations et portées sans toucher à cette identité.
- Les artefacts de tous les documents sont écrits sans valeurs par défaut ni `text_norm` (`SCHEMA_VERSION=4`, `server/ingest/artifacts.py`). La version du schéma entre dans **chaque** `ingest_fingerprint` : l'incrémenter ré-ingère les **trois** documents et périme leurs gates. `"3"` ajoutait `Document.parcours` — les conditions de profil que la `timeline` du guide attache à ses fiches (story 2.3), vide pour un contrat. `Block.structural_kind` est un enrichissement optionnel du typage : il est omis des documents non typés et ne change donc pas leur format sérialisé.

## Client LLM

Le client Claude unique des étapes vit dans `server/app/llm/` (story 1.3) ; aucune étape n'appelle le SDK directement.
Sonnet au minimum pour tout choix sémantique : comprendre, sélectionner la suffisance retrieval,
rédiger et vérifier utilisent le tier `reason`. `micro` reste une capacité technique et un axe
d'éval, jamais le défaut d'une décision sémantique servie.

- `models.py` : `TIERS` (`ingest` = Opus 5 Batch, `reason` = Sonnet 5 cache 1 h, `micro` = Haiku 4.5 daté), `STEP_TIERS`, `MODEL_CAPS` (effort/temperature/TTL par modèle), `EFFORT`, `model_for(tier)` ; `--check` vérifie les IDs contre l'API.
- `pricing.py` : la seule table de prix (USD/MTok, lecture de cache 0,1×, écriture 1,25× en 5 min / 2× en 1 h, `BATCH_DISCOUNT=0.5`) ; `cost_from_usage` chiffre en euros **uniquement** depuis l'`usage` renvoyé par l'API ; `estimate_cost` est la borne haute avant appel (préfixe et schéma de sortie au tarif d'écriture de cache du TTL du modèle, messages au tarif d'entrée, sortie à `max_tokens`, caractères par token calibrés sous le pire mesuré).
- `budget.py` : `RequestBudget(deadline_s, max_attempts, max_cost_eur)` — deadline monotone, compteur d'appels et cumul de coût partagés par toutes les étapes d'une requête.
- `prompting.py` + `prompts/` : `untrusted(kind, text)` délimite le contenu non fiable (balise fermante neutralisée), `load_prompt` lit les prompts versionnés (`commun.md` : règles de non-confiance) couverts par `prompts_digest`.
- `client.py` : `LlmClient.parse(tier, system_prefix, messages, output_model, budget, step, …)` — sorties structurées (schéma Pydantic), bloc système unique avec `cache_control` (préfixe byte-identique), délai dérivé de la deadline restante pour **chaque** appel — `min(max(llm_timeout_s, min(llm_timeout_s × llm_timeout_facteur, restant − llm_latence_marge_s)), restant)`, hors du corps envoyé, 1 retry sur parse invalide si la marge le permet, plafonds d'appels et de coût **avant** l'appel, mapping exhaustif des erreurs SDK vers `LlmUnavailable` (ou `Timeout` pour `APITimeoutError`) — `LlmParse` (parse invalide après retry, refus) et `BudgetExceeded` (plafonds) sont produits par le client lui-même, jamais mappés depuis une erreur SDK —, chaque appel tracé en `LLMCall` — y compris l'appel en échec (timeout, 429, 529, réseau : usage nul, durée réelle) ; `ResponseCache` (protocole) + `MemoryResponseCache` pour le cache d'évals ; `count_tokens` au tokenizer réel.
- `python -m server.evals.tokens <fichier…>` : tokens réels d'un fichier par tier (a servi à compacter les sommaires, voir `docs/tests-live.md`). Exige une racine de publication installée et refuse avant tout appel payant : le comptage est un lecteur de production, il pince une génération et lit chaque fichier **une** fois. Le comptage lui-même reste dans `server/app/llm/tokens.py`, sans aucune E/S.
- `tests/test_client_live.py` fait un appel réel par tier quand la clé est là (fixtures brutes committées dans `tests/llm_fixtures/`, rejouées sans clé).

## Étapes du pipeline

Les étapes vivent dans `server/app/steps/` (stories 1.4 et 1.5). Chacune est une fonction `Entrée → Sortie` qui crée et renvoie **son** `StepTrace` ; aucune étape n'en importe une autre (`tests/test_layers.py`), et `steps` ne connaît que `domain`, `corpus`, `llm`, `config`. L'enchaînement, les court-circuits et la relance sont l'affaire du pipeline (ci-dessous).

- `comprendre.py` — un appel `reason` : question + historique + profil → **deux sorties typées exclusives** (AD-5) : `ParsedQuestion` (intent, question résolue **autonome**, langue, termes toujours en français, `scope` dérivé du profil déclaré), ou `ClarificationRequise` quand une anaphore reste irrésoluble avec l'historique — dans ce cas aucune `question_resolue` n'est construite, ni inventée ni reprise telle quelle, et c'est la question à poser à l'utilisateur qui est rendue. Le modèle répond dans un schéma plat à champs requis, converti ensuite dans le modèle du domaine : un schéma sans valeur par défaut force le modèle à tout remplir, et l'exclusivité des deux issues y est un invariant — sa violation emprunte la relance motivée du client plutôt qu'un arbitrage du code. `lang` explicite l'emporte sur la détection et n'accepte que `fr`, `en`, `de`, `pt` ; une valeur hors liste est refusée avant l'appel. Sans forçage, une détection illisible ou non servie retombe sur `fr` avec `lang_fallback=true`. Le préfixe système est statique (`prompts/commun.md` + `prompts/comprendre.md`) — pas de sommaire, l'intent et les termes n'en ont pas besoin.
- `retrouver.py` — trois implémentations sous le même contrat de records scorés. `outils` est le défaut et utilise au minimum Sonnet au tier `reason`, deux tours bornés, un sommaire exhaustif paginé et les outils `sommaire`, `chercher`, `ouvrir_noeud`, `definitions`. `deterministe` reste du code pur et `full_context` un fallback borné. Toutes transportent score question-clause, titre, extrait et identités jusqu’aux décisions d’admission et de suffisance, avec snapshots opens/blocs/tokens et `sufficiency_result_uid` ; une clause du bon kind mais hors sujet ne clôt jamais la recherche.
- `rediger.py` — un appel `reason`, sortie `AnswerDraft`. Préfixe cacheable 1 h byte-identique = `prompts/commun.md` + `prompts/rediger.md` + **sommaire versionné** du document ; historique, blocs (**précédés de leur `block_id`**) et question résolue viennent après le breakpoint, chacun délimité par `untrusted()`. La consigne finale nomme la langue de rédaction en clair et impose que les quotes restent recopiées mot pour mot dans la langue du bloc. Les invariants du domaine (`claim_id` uniques, `claim_ids` connus, segment `factuel` ⇒ au moins une claim, une quote par bloc) sont validés **au parse** : un draft incohérent déclenche la relance motivée du client, puis `LlmParse`. `motif` (relance de la story 1.5) s'ajoute au dernier message utilisateur, lui aussi délimité par `untrusted()`. Les bornes chiffrées annoncées au modèle (`quote_min_chars`, `quote_max_chars`, `draft_max_segments`, `draft_max_claims`) sont rendues dans le prompt depuis `config.py` (`prompting.render_prompt`) : régler un seuil ne peut plus désynchroniser ce que le modèle produit et ce que le code acceptera. *Rédiger* refuse un `doc_id` qui ne recouvre pas les blocs reçus, avant tout appel : le sommaire du préfixe situe les blocs, il ne peut pas venir d'un autre document.
- Coût : `comprendre_max_tokens` et `rediger_max_tokens` bornent la sortie de chaque appel, `retrieval_max_blocks` et `retrieval_max_tokens` bornent ce que *retrouver* envoie à *rédiger* — ce sont les postes qui font tenir la chaîne sous le plafond de 3,50 € par requête, majorant `estimate_cost` compris. `RequestBudget` mémorise les préfixes déjà écrits dans la requête : un second appel au même préfixe est estimé au tarif de lecture de cache (0,1×) et non d'écriture.
- `verifier.py` — le contrôle, en deux moitiés. **Code pur** d'abord, pour chaque quote : le `block_id` existe, le bloc n'est pas un `heading`, la quote normalisée fait au moins `quote_min_chars` (ou `quote_min_ratio` du bloc), elle est **incluse** dans le `text_norm` du bloc **relu depuis le corpus** — jamais le texte du draft —, et son occurrence n'est pas ambiguë (le même passage dans un second bloc du document attribuerait la phrase au mauvais endroit). Les offsets de l'occurrence et les `line_ids` traversés sont conservés pour le surlignage. Une claim est `retrouvee` **ssi toutes** ses quotes le sont. **Un seul appel `reason` groupé** ensuite, sur les seules claims retrouvées : « ces passages soutiennent-ils l'affirmation **et** répond-elle à la question ? » — le modèle ne rend qu'un booléen par `claim_id`, aucun texte libre. `found` et `complete` sont calculés **par le code** (AD-4). Un verdict manquant n'est jamais deviné : la claim est écartée et un `CheckResult` le dit. Rien de ce qui vient du modèle ne traverse un motif en clair : un `block_id` inconnu du corpus devient `<bloc inconnu>` ; un `block_id` connu, lui, est notre propre chaîne, et c'est ce qui rend la relance actionnable.
- `restituer.py` — aucun modèle (AD-9). `Answer.texte` est rendu **déterministement** depuis les segments survivants : un segment `factuel` dont toutes les claims ont été rejetées est retiré, et les `claim_ids` des segments conservés sont ramenés aux claims survivantes. Un refus rend un unique segment `limite` porteur d'une phrase composée par le code — une par `kind` d'`AbsenceProof`, pour que « hors périmètre » ne se confonde pas avec « rien trouvé » ni avec « rien qui tienne la vérification ». Une **lecture partielle** (story 4.2f) est la troisième issue de cette fabrique : ni réponse, ni absence prouvée, mais une phrase propre (un registre de plus, guide et sinistre) et une `LecturePartielle` qui chiffre ce qui a été lu, là où la chaîne levait auparavant un échec terminal. Les constats du code sont des `Lacune(kind, n)` jusqu'à cette étape, qui les rend depuis un registre complet `fr/en/de/pt`, comme les quatre motifs de refus des registres guide et sinistre. Un refus conserve donc la langue servie ; `lang_fallback` ne signifie plus qu'un repli de détection.
- `tests/test_steps_live.py` rejoue trois scénarios réels sur le corpus `lux-guide` (profil famille → `scope`, question météo → `intent` seul, chaîne complète → ébauche citée sur deux fiches).

## Le pipeline du guide

`server/app/pipelines/guide.py` (story 1.5) enchaîne les cinq étapes — *comprendre → retrouver → rédiger → vérifier → restituer* — et rien d'autre. La couche `pipelines` **ne voit ni `corpus` ni `llm`** (table des couches du spine, vérifiée par `tests/test_layers.py`) : le corpus, l'index et le client lui arrivent en paramètres. Ce n'est pas un renoncement au typage, c'est l'invariant lui-même — un pipeline qui ne peut pas importer `llm` ne peut pas appeler un modèle hors d'une étape, ni sauter la vérification.

Ce qu'il ajoute aux étapes :

- **Les bornes d'entrée.** Le `RetrievalBudget` est rempli depuis `config.py` (`max_blocks`, `max_tokens`) ; un historique de plus de `historique_max_turns` tours est **refusé**, jamais tronqué (`InvalidRequest`, avant le premier appel : une requête refusée ne coûte rien) ; la deadline monotone est vérifiée avant chaque étape.
- **Les court-circuits.** Un `intent` hors périmètre, une clarification requise ou un retrieval vide vont directement à *restituer*, **sans** appel `reason`. Le court-circuit « zéro bloc » est distinct de celui d'AD-5, fondé sur le dictionnaire, qui reste désactivé tant qu'aucun humain n'a validé `data/dictionary.json` (story 2.1) : ici *retrouver* a bel et bien cherché, et l'`AbsenceProof` dit ce qui l'a été — jamais que l'information n'existe pas.
- **La relance, une seule fois.** Un défaut de **citation** (quote introuvable, bloc `heading`, quote trop courte, citation ambiguë) relance *rédiger* avec le motif précis composé par *vérifier* ; une ébauche identique (même hash canonique) arrête là. Une claim écartée par le seul jugement de pertinence ne déclenche pas de relance quand la réponse tient déjà : elle est conservée dans `rejected_claims[]`, et un second appel `reason` coûterait le tiers du budget d'une requête (seuil `relance_sur_non_pertinence`, à mesurer avec les questions-témoins). Quand **rien** n'a survécu, la relance part de toute façon : elle est le seul chemin vers une réponse.
- **Une relance qu'on ne peut pas payer ne jette pas la réponse.** AD-1 dit « aucun retry ne démarre sans marge » ; la même règle vaut pour les euros. Si le plafond par requête ou la deadline arrêtent la relance, la **première** vérification fait foi et la trace porte `relance_abandonnee`. Un draft relancé mais non vérifié n'est jamais montré.
- **La trace.** Étapes, tiers, durées, usage et coût réel, blocs ouverts et écartés, contrôles, seuils actifs, digests du pipeline et des prompts, `source_hash` et `ingest_fingerprint` du document — et **jamais** le texte d'un bloc.

Toute sortie normale — réponse, refus, clarification, claims toutes rejetées — est un `Answer` complet ; seules les entrées hors bornes et les échecs terminaux des étapes remontent en exception (l'API en fera des 4xx/503 en story 1.6). `tests/test_pipeline_live.py` rejoue deux scénarios réels : une question du guide dont chaque phrase affichée est soutenue, et un refus météo qui n'atteint jamais l'étage `reason`.

## Le verdict de sinistre

`server/app/domain/verdict.py` (story 1.8) est le découpage d'exécution d'AD-6 : **le modèle extrait des valeurs typées, le code décide.** Le module ne connaît ni le corpus, ni le client, ni les étapes — un test de couches le verrouille —, ce qui rend la table jouable ligne par ligne sans réseau (`tests/test_verdict.py`).

- `applicable_de_claim()` dérive `ClaimStatus.applicable` d'une claim retenue : `None` si elle ne cite aucune clause décisionnelle (une définition n'a pas d'applicabilité) ; `humain` si le `kind` d'un bloc cité n'est pas confirmé, si la clause n'a pas de portée déclarée, ou si les champs typés n'ont pas été rendus — **jamais** une valeur devinée. Vient ensuite la seule distinction qui fait tout le travail : `fait_requis_present=false` **sans** `fait_manquant` veut dire que le fait est *connu et contraire* — la clause ne vise pas ce cas —, tandis qu'un `fait_manquant` renseigné veut dire que le fait est *inconnu*. La première lecture n'est ouverte qu'aux `garantie` et `exclusion` : sur une `condition` ou une `franchise`, elle ne se distingue pas de « la condition n'est pas remplie », et la traiter comme inapplicable laisserait passer un `couvert` sur un dossier en défaut.
- `decider()` applique la table exclusive, dans l'ordre : contradiction déclarée par le corpus (`Block.relation.contredit` entre deux claims **affichées**) ou renvoi non résolu sur une claim décisionnelle ⇒ `ne_tranche_pas` ; aucune claim affichée de kind `garantie` ou `exclusion` ⇒ `ne_tranche_pas` ; exclusion `oui` dont la portée (`Document.scope_nodes()`) couvre les nœuds du cas ⇒ `non_couvert` ; garantie `oui` avec une condition ouverte ou hors du socle (`Node.scope.kind == "commun"`) ⇒ `sous_conditions` ; garantie `humain` **par** une option ou les conditions particulières ⇒ `sous_conditions` ; garantie du socle `oui` et rien d'ouvert ⇒ `couvert` ; sinon `ne_tranche_pas`. Le verdict porte sur les claims **affichées**, après le filtre `non_citee` d'AD-4 : un verdict adossé à une clause que l'utilisateur ne voit pas contredirait « rien d'affiché sans preuve ».
- **Ce qui empêche un `couvert` de complaisance est du code, et il a été mesuré.** La table peut rendre `couvert` — c'est une garantie du socle qui s'applique, aucune clause ouverte —, mais un `couvert` ne dit jamais que le sinistre sera indemnisé : il dit qu'aucune clause des conditions générales retrouvées ne s'y oppose. `MissingPackage` accompagne donc **tous** les verdicts, `couvert` compris, et `ask_client` réclame les quatre pièces qui n'ont pas été lues. Ce qui corrobore le `oui` d'une garantie n'est pas une politique globale mais l'établissement des qualités que la clause exige : le modèle **énumère** ces qualités et, pour chacune qu'il dit établie, cite un fragment des faits déclarés ; le code relit ce fragment mot pour mot dans les faits **et** exige qu'il emploie les mots de la qualité. Mesuré sur deux runs réels du cas témoin : le modèle a cité trois fois le même fragment — « Une bougie allumée posée sur une table basse est tombée sur le canapé » — pour établir « caractère soudain », « action subite de la chaleur » et « contact direct avec un foyer ». Authentique, et n'établissant aucune des trois : le code les refuse toutes, la garantie vaut `humain`, et les trois qualités partent en questions au client. Un modèle qui n'énumère rien rend son jeu de champs typés inexploitable — jamais un `oui` par défaut.
- `reason`, `ask_client[]` et `escalate[]` sont **composés par le code** depuis la règle qui a tranché et les booléens typés. Une question par pièce du paquet manquant (options, conditions particulières, avenants et date d'effet) : les annoncer absentes sans les demander laisserait le gestionnaire deviner. Seuls les libellés de `fait_manquant` viennent du modèle — bornés par `fait_manquant_max_chars` (au-delà, ignorés, jamais tronqués : une demi-phrase de fait manquant induit en erreur), dédupliqués, et bornés en nombre par la place que les questions du paquet laissent dans `ask_client_max`, pour que `missing.faits` et `ask_client` disent la même chose. Ils n'entrent jamais dans `Answer.texte`.

## Le pipeline du sinistre

`server/app/pipelines/sinistre.py` (story 1.8) rejoue **les cinq mêmes étapes**, dans le même ordre : le sinistre n'en fabrique aucune. Ce qui change tient aux consignes, au document et au verdict.

- **Les prompts.** `comprendre_sinistre.md`, `rediger_sinistre.md` et `verifier_sinistre.md` s'ajoutent à `prompts/` ; les étapes gagnent un paramètre `prompt` dont le **défaut est le guide**, si bien que son préfixe reste byte-identique et ses fixtures live rejouables. *comprendre* reçoit en plus les `Faits` déclarés (AD-5 les nomme déjà), délimités par `untrusted()`. *rédiger*, lui, ne les voit pas : ils lui arrivent repliés dans la question résolue, et le prompt le dit.
- **Un seul appel `reason`, toujours.** `SortieVerifierSinistre` hérite de `SortieVerifier` et ajoute `applicabilite[]` : pertinence, phrases soutenues, couverture des facettes et champs typés sortent du **même** appel (AD-9 amendé — « jamais un second appel »). Son plafond de sortie est distinct (`verifier_sinistre_max_tokens`) parce qu'il rend une entrée de plus par clause : à `verifier_max_claims` claims, le partager avec le guide ferait tronquer la réponse, donc un `LlmParse`, donc un sinistre **sans verdict**. Le schéma n'offre au modèle aucune place pour un verdict : ni `applicable`, ni `couvert`, ni `value`.
- **Une seule clause par affirmation** (AD-6). Le contrôle est en code, sur le typage de l'ingestion : une claim dont les blocs cités portent deux `kind` décisionnels différents est rejetée `ambigue` avec un motif actionnable — donc elle emprunte la relance unique d'AD-3. Une clause jointe à sa définition ou à son paragraphe d'introduction reste admise : c'est son contexte.
- **La recherche préfère les clauses, elle ne s'y limite pas.** `Index.chercher(kinds_prioritaires=…)` place les blocs `garantie|exclusion|condition|franchise` devant les autres **à score égal** — le départage vit dans l'index parce que le score n'existe que là. Il ne filtre par aucun kind, mais il change qui survit à `limit`. À J+1 le typage est manuel et ne couvre que quatre blocs du contrat : le rappel repose encore surtout sur les termes, et c'est le typage automatique (epic 3) qui lèvera la limite.
- **Aucun repli, et jamais un refus muet** (AD-16). Une variante inconnue, des faits hors bornes ou mal formés, un budget et une deadline passés ensemble sont des `InvalidRequest` levées **avant** le premier appel facturé ; un contrat non servi est un `CorpusUnavailable`. Et tout refus — hors périmètre, aucune clause trouvée, toutes les citations rejetées — porte un verdict `ne_tranche_pas` composé par le code, avec les questions du paquet manquant : c'est le dossier qui a le plus besoin d'être complété. *restituer* choisit son **registre** de phrases (`REGISTRE_SINISTRE`) pour que le refus parle du contrat et non du guide.
- Les invariants de relance partagés par les deux pipelines — dominance sur tous les axes, deux appels indissociables, motifs de citation — vivent dans `server/app/pipelines/commun.py`. Le `Verdict` n'entre pas dans la comparaison : ses quatre valeurs n'ont pas d'ordre, et préférer une relance pour ce qu'elle conclut serait exactement ce qu'AD-6 empêche.
- `tests/test_sinistre_live.py` rejoue le cas témoin de la bougie sur le contrat AXA réel, enregistré puis rejouable sans réseau ; le relevé est dans `docs/tests-live.md`. La route HTTP et la page `/sinistre/` sont la story 1.9.

## Le serveur HTTP

`server/app/api/` (stories 1.6, 1.9, 1.10, 3.4 et 3.5). **Une seule origine** sert tout (AD-12) : `/` (l'accueil, `tools/accueil/`), `/guide/` (la copie du site, fichiers jamais renommés), `/sinistre/` (l'outil sinistre), `/sinistre/ingestion/{doc_id}` (audit d'ingestion), `/api/v1/chat`, `/api/v1/sante`, `/api/v1/sinistre`, `/api/v1/documents`, `/api/v1/documents/{doc_id}/report`, plus les alias historiques `/chat` et `/sante` attendus par `reponseApi()`/`testerApi()`. Aucune configuration CORS : il n'y a pas de seconde origine à autoriser.

- **Les routes du sinistre n'ont pas d'alias historique** (story 1.9) : AD-11 n'en prévoit que pour `/sante` et `/chat`, parce que le `chat.js` du site les attend. Rien n'attend `/sinistre` ni `/documents` à la racine, et un alias de plus serait une route inventée par story. `/documents` et `/report` ne coûtent rien (tout est chargé au démarrage) et ne sont donc **pas** limitées, comme `/sante` ; `/sinistre` l'est, comme `/chat`, par la même dépendance de routeur.
- **L'audit d'ingestion est séparé du working set** (story 3.5) : `/api/v1/documents` liste les documents servis et les quarantaines auditables avec leur statut effectif, mais seuls les contrats servis sont sélectionnables et soumettables. Rapports, empreintes, gate, édition et URL publique filtrée sont lus une fois au démarrage ; les requêtes ne relisent pas `data/`. Une clé de manifest non publiable n'entre ni dans la liste ni dans un chemin, mais sa quarantaine reste annoncée sur `/sante` sous `doc_id="*"`, sans URI ni chemin privé dans sa raison.
- **`POST /api/v1/sinistre`** rend `{answer, sources, via, trace}`. `sources[]` porte des `ClauseSource` : la citation relue du corpus, plus `page`, `bbox`, `line_ids`, `kind` et `kind_confirmed` **lus sur le bloc** (AD-6 : `Block.kind` est la seule source de typage — le front n'a pas de corpus et ne peut pas inventer le type d'une clause, ni taire qu'il n'est pas confirmé). Deux refus en 400 **avant tout appel facturé** : un `doc_id` que le service ne sert pas (le pipeline lèverait un 503, qu'AD-16 réserve à une indisponibilité passagère — or le corpus est chargé une fois et ne bouge plus), et un `doc_id` servi qui n'est **pas** un contrat (soumettre un sinistre au guide dépenserait quatre appels pour un `ne_tranche_pas` acquis d'avance). Le `dossier` du pipeline — ce que l'appelant détient déjà du paquet contractuel — n'est **volontairement pas** exposé par la route : sur un démonstrateur public, un booléen « j'ai les conditions particulières » est une auto-déclaration invérifiable qui referme la seule question que l'outil sait poser, et la promesse affichée est « au regard des conditions générales seules ».

- **Au démarrage, une seule fois** (`api/etat.py`) : les digests du pipeline et des prompts (ils relisent toute l'arborescence du code — les calculer par requête, ou les laisser au repli mémoïsé du pipeline, ferait servir des empreintes périmées sans que rien ne le dise), le `GateContext` de l'image, le corpus en lecture seule, l'index, le client Claude async. Une requête ne recharge rien.
- **Tout ce que le pipeline rend est un 200** (AD-11) : réponse, refus, clarification, affirmations toutes rejetées. Le corps porte `{texte, segments, sources, fiches, unknown, comparateur, answer, via: "api/v1", trace}`. `sources[]` ne contient que des citations **relues du corpus** (`VerifiedQuote`) — une citation que le validateur n'a pas retrouvée est restée la chaîne du modèle, et elle n'est pas affichée ; elle reste lisible dans `answer.rejected_claims`, où sa nature est explicite.
- **Les échecs sont terminaux, jamais dégradés** (AD-16) : une seule enveloppe `{error: {code, message, request_id}, trace?}`, les codes de `domain/errors.py` et rien d'autre. `400 invalid_request` pour une borne du contrat (question > 1 000 caractères, historique > 6 tours — **jamais tronqué** —, variante inconnue, ou `lang` hors de `fr/en/de/pt`), avant tout appel facturé ; `413 input_too_long` pour un corps HTTP au-delà de `request_max_bytes` (refusé avant d'être lu), `429 rate_limited`, `503` pour les pannes du pipeline (avec la trace partielle), `500 internal` générique pour l'imprévu. Un fichier statique absent reste un 404 nu : lui inventer un code serait précisément ce qu'AD-16 interdit.
- **Un identifiant par requête** (AD-10) : uuid4 posé par `api/request_id.py`, rendu en `X-Request-Id`, repris dans la `Trace` et dans l'enveloppe d'erreur. Une ligne JSON par requête sur la sortie standard, avec `intent`, `found`, `verdict`, `reason_kind`, `variants_count`, `blocks_scanned`, `cost_eur` — et **jamais** le texte de la question ni `terms_searched` (ils peuvent révéler santé, famille, argent). La liste des champs logués est close en code : une route ne peut pas la contourner. `X-Cloud-Trace-Context` est logué à part.
- **L'audit LLM en ligne est sans état** (AD-10/AD-15) : l'enveloppe exacte est détruite dès la projection de ses identités, hashes et tailles ; aucune liste mémoire du client partagé ne la retient. Seuls les runners et ingestions hors ligne explicitement contrôlés peuvent injecter le sink exact JSONL borné.
- **Le limiteur (`api/limiter.py`) est best-effort, par instance.** Il ne promet pas un quota global : ses compteurs vivent en mémoire de process (un redémarrage les remet à zéro, deux instances servent deux fois le quota), une adresse forgée par requête le contourne, et sa table est bornée (`rate_limit_max_clients`, la plus ancienne identité évincée repart de zéro). Ce qu'il protège, c'est le budget d'une démonstration servie par une seule instance — avec le plafond par requête (3,50 €) et le plafond fournisseur derrière lui. L'identité est le premier élément de `X-Forwarded-For`, lu directement dans l'en-tête (IPv4 entière, IPv6 tronquée au /64, parce qu'un abonné se voit déléguer un /64 entier). `Retry-After` annonce le reste de la fenêtre dépassée, borné par `retry_after_s`.
- `/sante` n'est jamais limitée (le front la sonde à chaque chargement de page) et publie ce qui a été calculé au démarrage : `ok`, `version` (le `sha7`, projection de `GIT_SHA` qui porte la révision complète), `documents_servis`, `gate_profile` et `gate_cases` (**`null` tous les deux** dès qu'un document servi n'a pas de gate valide — annoncer un profil qu'un document ne porte pas serait une bascule silencieuse, et un compte sans profil serait la même, chiffrée), `dictionary.validated`, `alerts[]` (`sans_gate`, `gate_perime`, `source_absente`, `rapport_illisible`, quarantaine — dont `bloquant_statique` —, et `ungated_refuse_en_production`) et les seuils actifs.
- `comparateur` est calculé par la règle du site (`web/app/chat.js`, `toucheContrats`) transposée telle quelle sur la question normalisée : AD-11 le conserve « pour l'UI existante », et le laisser toujours faux retirerait une fonction du site en silence.

## Le front du guide

`web/` (story 1.7). La copie du site est servie sous `/guide/` ; seul son onglet **Assistant** a changé, et seulement là où le contrat d'AD-11 l'exigeait — aucun fichier renommé, aucun framework, aucune étape de build.

- **Il parle au serveur qui le sert** (AD-12) : `API_BASE` est l'origine courante, la sonde `/sante` tourne sur toute origine, le profil part **brut** (objet) et l'historique en `{role, texte}`, borné à six tours, le dernier tour utilisateur exclu quand il répète la question, un tour de plus de 2 000 caractères écarté plutôt que coupé. Le champ `contexte` de l'ancien relais a disparu : il recopiait plus de 20 ko de fiches que le serveur n'a jamais lues.
- **Il montre ce sur quoi il repose** (AD-3 / FR4) : chaque segment factuel est suivi de **ses** citations — le passage relu du corpus par le serveur, la fiche, le lien officiel, et le statut « retrouvée · pertinente · édition … — actualité non vérifiée ». L'appariement citation ↔ phrase refait l'énumération de `presenter.sources_de()` et vérifie chaque `block_id` ; au moindre désaccord il abandonne et montre la liste plate, plutôt que d'attribuer une citation à la mauvaise phrase (un test serveur verrouille cet ordre). Un refus affiche la phrase composée par `restituer` **plus** la preuve chiffrée d'AD-4. En pied : l'état (sûr / partiel / inconnu) et le coût réel lu sur `trace.total_cost_eur`.
- **Il dit ce qui est traduit** (story 2.4) : pour une réponse non française, le pied précise que la réponse est traduite depuis le guide français et que les passages cités restent dans leur texte source. Si la détection a dû retomber sur le français, une seconde mention le dit. `answer.lang` et `answer.lang_fallback` sont relus strictement ; un type cassé produit `reponse_illisible`, pas une réponse peinte à moitié.
- **Il n'a aucun repli silencieux** (FR11 / AD-16) : sur 503 ou panne réseau, un bandeau et un bouton à cliquer ; le moteur lexical du site ne tourne qu'après ce clic, et le résultat porte `via: "local"`. Sur 4xx/429, un message français composé à partir du `code` — jamais le `message` du serveur, qui est un diagnostic pydantic — et **aucun** bouton. Même quand la sonde a échoué au chargement : le badge dit « mode indisponible » et la première question affiche le bandeau, plutôt qu'une recherche de mots-clés servie comme si elle avait été vérifiée.
- **Il ne stocke rien de ce qui a été dit** (AD-15) : le `localStorage` ne porte plus que le profil et les préférences d'affichage ; la persistance des conversations héritée du site est retirée, et une conversation déjà enregistrée est réécrite sans elle au premier chargement. Tout texte reçu du serveur est rendu par `textContent`. La mention « où part votre question » vit sous la saisie, dans l'onglet comme dans le panneau flottant.
- **Son badge dit le niveau de validation du corpus servi** (story 1.10) : « mode api · vertical (2 cas) » quand les documents servis portent un gate, « mode api · non validé » quand ils n'en portent pas. `testerApi()` lisait déjà `gate_profile` et `alerts` sur `/sante` et les jetait ; le badge disait « mode api » de la même façon que le corpus soit mesuré ou pas du tout. Le suffixe est composé par une fonction **pure** (`libelleMode(via, validation)`) que `ui.js` se contente de poser dans les deux surfaces ; il ne vaut que pour le mode api, et une sonde illisible ou muette ne suffixe **rien** plutôt que d'annoncer un niveau que personne n'a lu.
- **Il borne son attente** : la requête est abandonnée au-delà de `deadline_s` (lu sur `/sante`) plus une marge, et l'abandon est une indisponibilité comme une autre. Les bornes du contrat viennent du serveur — `historique_max_turns` est lu sur `/sante`, pas recopié —, sauf `Turn.texte`, qui est une contrainte de schéma et qu'un test amarre à `Turn.model_fields`.
- **Les citations sont groupées sous le paragraphe, pas sous chaque phrase** (story 5.6, L2) : une puce par fiche, « Les huit premiers jours · 5 passages », et le clic ouvre la fiche **et** la fait défiler jusqu'à la première phrase citée, surlignée. La recherche du passage passe par une carte normalisée (apostrophes typographiques, guillemets, espaces insécables, casse) qui conserve un index vers le texte d'origine : le surlignage porte donc sur la fiche telle qu'elle est écrite. Le corpus servi et `kb.js` peuvent diverger — la fiche s'ouvre alors en haut, sans erreur et sans surlignage inventé. Le statut « retrouvée · pertinente · édition … » reste, sous les puces, en plus discret.
- **« Source officielle » n'est affiché que si l'adresse mène à la page dont on parle** (story 5.6, L2) : règle **mécanique**, pas une liste de sites — le chemin doit porter au moins deux segments qui disent quelque chose, un code de langue et un nom de page d'accueil n'en disant rien. `guichet.public.lu/fr/citoyens/citoyennete.html` passe, `luxembourg.public.lu/fr/vivre.html` non. Omis veut dire omis : rien ne le remplace, surtout pas une autre adresse.
- **L'attente est habillée** (story 5.6, L2) : trois étapes nommées — « Je lis les fiches › J'écris › Je vérifie » —, celle en cours marquée et animée, un chronomètre, et l'ordre de grandeur attendu. Elle suit le flux `POST /chat/progression` quand le serveur en sert un, et estime l'avancement sur le temps écoulé sinon — l'écran **dit** laquelle des deux il montre. `prefers-reduced-motion` coupe l'animation, jamais l'information. Un seul appel facturé par question : la bascule vers la route classique n'a lieu que sur 404/405 (rien n'a tourné) ou sur un flux coupé avant son résultat, jamais après qu'un résultat a été reçu, et un 404 vaut pour la session.
- **Il se teste sans navigateur, y compris ce qu'il affiche** : `chat.js` ne compose pas du DOM mais une **description** de ce qu'il faut peindre (`vueReponse`, `vueErreur`, `vueAttente` : un arbre de `{tag, cls, texte, enfants, action, href}`), et `ui.js` n'est plus qu'un matérialiseur sans décision. Les actions sont **décrites** (`{nom: "recherche_simple", question}`), jamais des fermetures : c'est ce qui permet d'affirmer par un test que le bandeau d'indisponibilité porte exactement une action de repli et qu'un 4xx n'en porte aucune — la règle d'AD-16 que rien ne voyait tant que la composition vivait dans le DOM. `tests/js/chat_cases.mjs` charge `chat.js` dans un `node:vm` avec `window`, `location`, `fetch` et les minuteurs doublés ; `tests/test_web_chat.py` asserte les relevés. Aucune dépendance ajoutée. Le rendu final reste vérifié en live (`docs/tests-live.md`).

## Le front du sinistre

`tools/sinistre/` (story 1.9). Une page autonome, sans build, sans framework, sans requête tierce — et **sans** dépendance à `web/app/styles.css` : « style du site » est lu comme sa sobriété (même pile de polices, mêmes cartes arrondies, `color-scheme` clair/sombre), pas comme une feuille de 1 328 lignes taillée pour le DOM du guide, qu'une classe renommée là-bas casserait ici.

- **Quatre blocs fixes, jamais repliés, dans cet ordre** (story 5.6, L2) : **1. La réponse** (première phrase en serif, explication, verdict en pastille colorée, et « ce que je ne sais pas » en une ligne) ; **2. Sur quoi je m'appuie** (une carte par clause : chemin « 3.1.4 Dégâts des eaux › Étendue de la garantie », page, **paragraphe entier** avec la partie citée surlignée, et sous la clause la phrase en clair de l'affirmation qui la cite — les clauses que la table a jugées non applicables passent en retrait, après les autres) ; **3. Ce qu'il me manque pour aller plus loin** (les questions décisives avec leurs boutons Oui / Non / Ne sait pas et la réponse libre, les faits exigés, et les pièces non lues en une ligne grise) ; **4. Garde-fous** (« N citations relues mot pour mot », « M phrases retirées », la règle du verdict, l'état de la réponse, et les affirmations écartées derrière un dépliant). Le dossier conversationnel — faits et provenance, correction d'un fait, historique du verdict, copie du dossier — vient **après**, replié, sous le titre « Dossier ». Rien n'est replié au-dessus de la réponse ; c'était le défaut de la mise en production du 3 septembre.
- **Les libellés de verdict sont ceux d'un assuré** : `couvert` → « Couvert », `sous_conditions` → « Sous conditions », `non_couvert` → « Exclu », `ne_tranche_pas` → « Pas de clause qui s'applique » quand aucune affirmation n'a été retenue et « Je ne peux pas trancher » sinon. Aucune valeur brute ne reste à l'écran, et une valeur hors des quatre de `VerdictValue` se dit toujours telle quelle — la traduire en verdict connu serait le dégradé silencieux qu'AD-16 interdit.
- **Le paragraphe entier, avec la citation surlignée** : le moteur publie `texte_bloc`, `chemin` et `claim_id` sur chaque clause ; la page retrouve la quote dans son bloc par une carte normalisée (apostrophes typographiques, espaces insécables, retours à la ligne de la mise en page du PDF) qui conserve un index vers le texte d'origine. Introuvable, la quote s'affiche **seule**, et la page le dit : aucun surlignage n'est inventé. Au-delà de 600 caractères, l'écran montre la phrase citée avec une phrase avant et une après, plus un bouton « Voir le paragraphe entier » — dépliage à la demande, jamais l'inverse. Tant que le moteur ne publie pas ces champs, le repli est la quote seule et le titre du nœud lu dans `trace.blocs`.
- **L'attente est habillée** : trois étapes nommées — « Je lis le contrat › J'écris la réponse › Je vérifie chaque citation » —, celle en cours marquée et animée, un chronomètre, et l'ordre de grandeur attendu. Elle suit le flux `POST /api/v1/sinistre/progression` quand il existe et l'estime sur le temps écoulé sinon. Un seul appel facturé par soumission : bascule sur 404/405 ou sur un flux coupé avant son résultat, jamais après qu'un résultat a été reçu ; un corps SSE qu'on ne peut pas lire au fil de l'eau est lu d'un bloc plutôt que redemandé. `prefers-reduced-motion` coupe l'animation, jamais l'information ; `aria-busy` et le verrou de la saisie sont ceux d'avant.
- **Elle affiche, elle ne calcule pas** (AD-6 / AD-4) : aucune règle de la table du verdict n'est côté page. `answer.verdict` arrive décidé, avec sa raison composée par le serveur, et la page pose le verdict, la portée (« au regard des conditions générales seules — verdict non validé par un expert assurance »), la raison, **les faits compris** (`answer.faits_compris` : bien, événement, lieu, cause, moment — ce que *comprendre* a compris, pas la description en écho), le paquet manquant, les questions à poser, les clauses et la trace dépliable.
- **Les statuts se rattachent par `claim_id`, ou par position** : quand le moteur publie `sources[i].claim_id`, chaque clause **dit** quelle affirmation la cite. Sans lui, la page refait **la même** énumération que `presenter.clauses_de()` — `for claim in answer.claims for quote in claim.quotes` — en vérifiant chaque `block_id`. Au moindre désaccord elle abandonne, **le dit**, et affiche une liste plate : une clause attribuée à la mauvaise affirmation sous un verdict est pire qu'une liste sans rattachement.
- **Les clauses non retrouvées s'affichent sans leur citation** : `answer.rejected_claims` publie tout, y compris des quotes restées les **chaînes du modèle** (`non_retrouvee`, `ambigue`). La page montre le texte de l'affirmation et le motif du rejet en français — la même règle que celle qui les tient hors de `sources[]`.
- **Aucun repli, aucun verdict de remplacement** (AD-16) : sur 400, 429, 503 ou 500, la page affiche l'erreur et sa référence de requête, sans bouton et **sans conserver le verdict précédent** — le conteneur est vidé avant chaque peinture. Un 200 dont le corps n'est pas lisible (pas de `verdict`, pas de `trace`, une clause sans `kind`) est traité comme une panne, pas comme un verdict partiel.
- **AD-15** : avertissement « Démonstrateur public : ne saisissez aucune donnée réelle ou nominative de sinistre » au-dessus du formulaire, mention de confidentialité qui dit ce que la politique du fournisseur dit *réellement* (suppression sous 30 jours, et ses **quatre** réserves — service à rétention plus longue contrôlée par le client, accord de rétention différent, application de la politique d'usage, obligation légale — plus les deux ans du contenu signalé, avec le lien et la date de lecture), rien en `localStorage`, et tout ce qui vient du serveur posé par `textContent`.
- **Elle se teste sans navigateur, composition et peinture** : `sinistre.js` sépare les fonctions pures (`vueVerdict`, `vueErreur`, `vueFormulaire`, `appuisDe`, `trouverPassage`, `clausesParClaim`, `statutTexte`, `libelleVerdict`, `coutTexte`, `corpsSinistre`) d'un matérialiseur qui ne décide de rien. `tests/js/sinistre_cases.mjs` les charge dans un `node:vm` avec `fetch` et le DOM minimal doublés ; `tests/test_web_sinistre.py` asserte les relevés, y compris que les `maxlength` de la page sont **ceux des schémas du serveur**, que les libellés de verdict couvrent **toutes** les valeurs de `VerdictValue` (le test est paramétré sur le `Literal` du domaine), et qu'`innerHTML` ne sert qu'à vider un conteneur. `tests/js/sinistre_rendus.mjs` fait en plus traverser la page par **trois réponses entières figées** (`tests/data/front/*.json` : un cas couvert, un cas sous conditions, un cas où aucune clause ne s'applique, construites sur les blocs réels du contrat AXA) et relève ce que chacun des quatre blocs montre. Aucune dépendance ajoutée.

## Infrastructure

`scripts/gcp_bootstrap.sh` (idempotent, `--project=foyer-retour`, `europe-west1`) crée les comptes de service, la fédération d'identité GitHub, le secret, les buckets et le budget ; il affiche les quatre variables GitHub à poser (`GCP_PROJECT_ID`, `WIF_PROVIDER`, `DEPLOY_SA`, `SOURCE_READER_SA`). **Le lecteur CI est séparé du déployeur jusque dans le principal fédéré** : le mapping du provider produit `attribute.role=deploy` seulement avec le claim `environment=production` depuis `deploy.yml@main`, `attribute.role=source-reader` seulement pour `job_workflow_ref=byousoku-9/foyer-retour/.github/workflows/ci.yml@refs/heads/main`, et `none` sinon. `deploy.yml` attache donc son job déployeur à l'environnement GitHub `production`; les comptes sont liés respectivement aux principalSets `attribute.role/deploy` et `attribute.role/source-reader`. La migration passe d'abord par une condition `deploy`-only, pose le binding étroit du déployeur puis retire le binding repository historique; le lecteur n'est autorisé qu'ensuite, afin qu'aucun jeton de lecture ne puisse profiter de l'ancien binding large pendant la transition. Le provider reste en plus borné au dépôt et à `refs/heads/main`, et le bootstrap compare puis répare condition, mapping, issuer et état.

`source-reader@foyer-retour.iam.gserviceaccount.com` n'a aucun rôle projet, reçoit uniquement son `roles/iam.workloadIdentityUser` étroit et `roles/storage.objectViewer` sur `gs://foyer-retour-sources`. Après liaison, le bootstrap audite ces trois policies et échoue en nommant tout droit inattendu, sans le révoquer silencieusement. Le bucket source impose Uniform Bucket-Level Access et Public Access Prevention `enforced`; tout membre `allUsers` ou `allAuthenticatedUsers` bloque l'exécution sans retrait implicite. **Ce que le compte déployeur peut faire reste inchangé** : au niveau du projet, `run.admin`, `cloudbuild.builds.editor`, `artifactregistry.writer`, `serviceusage.serviceUsageConsumer` et `storage.bucketViewer`; agir en tant que runtime et compte de build; écrire dans les deux buckets de dépôt de source; et conserver son binding historique `roles/storage.objectViewer` sur le bucket source. Le flux de preuve CI, lui, n'authentifie jamais `DEPLOY_SA`.

Les PDF ne sont pas dans le repo. Pour chaque objet AXA ou Baloise, l'unique autorité SHA est `data/<doc-id>/source.sha256` : le script relit toujours les octets déjà présents; sinon il valide le fichier local puis tente une création atomique `--if-generation-match=0` avant de relire l'objet. `AXA_PDF_LOCAL` et `BALOISE_PDF_LOCAL` ne servent donc qu'à créer un objet absent, jamais à écraser. `scripts/hello_world/` reste le conteneur minimal qui a validé les rôles Cloud Run initiaux.

## Déploiement

Un push sur `main` déclenche `.github/workflows/deploy.yml`, et c'est le seul chemin vers la production. Il n'y a **qu'un** service (`foyer-retour`, `europe-west1`, projet `foyer-retour`) et **qu'une** origine : l'accueil, la copie du site, l'outil sinistre et l'API y vivent ensemble (AD-12).

**Ce que le workflow fait, dans cet ordre :**

1. **Il vérifie d'abord les sources réelles, puis la suite.** Le job `verifier` réutilise `ci.yml` avec `sources_reelles: ${{ github.ref == 'refs/heads/main' }}`. Après lint et installation, l'action `google-github-actions/auth` v3 épinglée au SHA vérifié `7c6bc770…b2cc093` demande pour `SOURCE_READER_SA` un `access_token` borné à 300 secondes et au scope `devstorage.read_only`, sans fichier de crédentiel; ce jeton n'est transmis qu'à `fetch_source --all --private-source`. Ce mode lit directement AXA et Baloise dans `gs://foyer-retour-sources`, vérifie leur SHA committé avant écriture, puis deux nodeids pytest nommés prouvent leur régénération avant la suite complète. Sur une PR, ou sur un `workflow_dispatch` lancé hors de `main`, l'entrée reste fausse : ni étape d'authentification ni accès privé; le job déployeur est déjà ignoré hors `main`.
2. **Il prend ensuite l'identité de déploiement, sans clé.** Dans le job suivant, `google-github-actions/auth@v3` échange le jeton OIDC de GitHub contre l'identité distincte du compte de service déployeur, par fédération directe (`permissions: id-token: write`). Aucune clé de compte de service n'existe dans le dépôt ni dans GitHub. Deux choses encadrent cette étape et n'y sont pas par hasard (revue Codex 1.11) : elle est précédée du contrôle des variables du dépôt, qui **refuse tout `GCP_PROJECT_ID` autre que `foyer-retour`** — une variable de dépôt s'édite depuis l'interface de GitHub, sans revue et sans diff, et une valeur erronée ferait déployer ailleurs — et de l'installation d'`uv`, un `curl | sh` qui n'a ainsi rien à voler : après `auth`, il tournerait sur un runner portant déjà le crédentiel fédéré du déployeur. Ce crédentiel (`gha-creds-*.json`, écrit dans le répertoire de travail) est exclu de `.gcloudignore`, `.dockerignore` et `.gitignore` : sans quoi il partirait dans le bucket de sources avec l'archive de `--source`. Et la frontière véritable est côté GCP : la condition du fournisseur d'identité fédérée borne le dépôt **et** `assertion.ref == "refs/heads/main"` — le `if:` d'un workflow ne dit rien à IAM.
3. **Il construit et déploie sans trafic.** `deploy-cloudrun@v3` avec `--source` : Cloud Build construit l'image (le PDF du contrat n'est pas dans le dépôt — `fetch_source --all` le télécharge au build, empreinte vérifiée, repli sur `gs://foyer-retour-sources/`), et la révision part **sans trafic**, sous le tag `candidat`. Le secret est monté à une **version épinglée** (`ANTHROPIC_API_KEY=ANTHROPIC_API_KEY:1`), et `GIT_SHA` porte le `sha7` du commit.
4. **Il sonde la révision candidate**, sur son URL taguée (`https://candidat---…`) et non sur celle du service — c'est ce que `deploy-cloudrun@v3` publie en sortie `url` dès que l'entrée `tag` est posée, et le workflow confronte cette sortie à l'URL qu'il relit sur `status.traffic[]` avant de sonder quoi que ce soit : `uv run python scripts/smoke.py --base-url … --version <sha7>` joue **quatre vérifications** —
   - `GET /api/v1/sante` : les trois documents servis, le `gate_profile` **et** le nombre de cas du manifest de ce commit, `version` = le `sha7` déployé, les seuils dont le smoke tire sa patience, et **aucune** alerte (une dérogation `ALLOW_UNGATED` posée à la main sur le service se voit ici) ;
   - les trois surfaces d'AD-12 — `/`, `/guide/`, `/sinistre/` — répondent 200 : un `COPY web` disparu du `Dockerfile` ou un montage statique cassé donnerait sinon une API parfaite devant trois pages mortes ;
   - `POST /api/v1/chat` : le cas témoin du guide, rejoué par HTTP — `via`, la réponse trouvée, au moins une claim `retrouvee`, l'empreinte de source du manifest ;
   - `POST /api/v1/sinistre` : le cas de la bougie, plus le verdict, qui doit tomber dans les valeurs admissibles écrites dans le cas.

   Les deux premières ne coûtent rien, les deux dernières appellent un modèle : **l'ordre est voulu**, un déploiement déjà refusé n'a pas à être confirmé à 0,08 €.
5. **Il promeut le trafic seulement ensuite, et vers la révision qu'il vient de sonder** : `update-traffic --to-revisions=<la révision taguée>=100 --remove-tags=candidat`. Nommer la révision plutôt que `--to-latest` n'est pas un détail : « la dernière créée » n'est pas forcément celle que le smoke a validée, et un déploiement lancé à la main pendant les quarante secondes du smoke recevrait sinon 100 % du trafic sans avoir jamais été vérifié.
6. **Si quoi que ce soit échoue, il retire le tag.** Un smoke rouge fait échouer le workflow **avant** la promotion, et la révision précédente garde 100 % du trafic ; mais la révision refusée resterait joignable sur `https://candidat---…` — publiquement, `--allow-unauthenticated` valant aussi pour l'URL taguée, et avec le secret Anthropic monté. Une étape `if: failure() || cancelled()` la détague — une annulation à la main, ou le plafond `timeout-minutes`, laisse exactement la même révision en vol qu'un échec. Il n'existe aucun chemin qui promeuve « quand même » (AD-16).

**Retour arrière.** Une révision servie qui se révèle mauvaise se retire sans rien reconstruire :

```bash
gcloud run revisions list --service=foyer-retour --region=europe-west1 --project=foyer-retour
gcloud run services update-traffic foyer-retour --to-revisions=<révision-précédente>=100 \
  --region=europe-west1 --project=foyer-retour
```

**Dimensionnement (AD-13), et la règle qui le protège.** Le service tourne en `--allow-unauthenticated --max-instances=1 --concurrency=2 --timeout=300 --min-instances=1 --memory=1Gi`. `deploy.yml` en est l'**autorité** — c'est le seul endroit qui les *décide* ; ce paragraphe et `docs/tests-live.md` ne font que les citer, et un test relit le workflow pour que la citation ne prenne jamais le pas sur la source. Ce sont des drapeaux d'infrastructure, pas des seuils de `config.py` (qui configure le processus). `--max-instances=1` est le **plafond dur** de la facture, avec le plafond de coût par requête et le plafond fournisseur. `--timeout` doit rester **strictement** au-dessus de `deadline_s` : à égalité, l'infrastructure couperait une requête que le pipeline honore encore, et le 503 viendrait d'elle au lieu de la seule autorité qui sait pourquoi (AD-16). Un test relit les deux fichiers pour le tenir. **Et l'ordre va jusqu'au navigateur** (AD-11, amendement AD-1 du 03/09/2026) : délai d'attente du client **>** `--timeout` Cloud Run **>** `deadline_s`, soit 315 s > 300 s > 165 s. En dessous de cet ordre, une requête coupée par l'infrastructure serait affichée comme un abandon du client, sans échec réel derrière ; le même test tient les trois nombres, qui vivent dans trois fichiers qui ne se lisent pas l'un l'autre. `--memory=1Gi` est posé pour la même raison que ce paragraphe le disait déjà : **deux requêtes de pipeline concurrentes avec PyMuPDF chargé dans les 512 Mio par défaut n'est pas une hypothèse tenable**, et le service tourne en `--concurrency=2`. Reconnaître la limite sans poser le drapeau revenait à la documenter au lieu de la corriger. **Le passage à `--max-instances=2 --concurrency=8` n'aura lieu qu'après un test mémoire/latence** — celui-là reste un chiffre qu'on ne pose pas sans mesure.

**Relancer un déploiement à la main.** `deploy.yml` accepte `workflow_dispatch`, mais le job de déploiement porte `if: github.ref == 'refs/heads/main'` : le bouton de GitHub laisse choisir la branche, et sans cette garde un « Run workflow » sur une branche de travail aurait construit et promu ce code en production. Sur une autre référence, le lint et la suite tournent et rien n'est déployé.

**Ce dont le workflow a besoin, et qui se pose une fois** : les quatre variables du dépôt affichées par `scripts/gcp_bootstrap.sh` — `GCP_PROJECT_ID`, `WIF_PROVIDER`, `DEPLOY_SA`, `SOURCE_READER_SA` (`gh variable set …`). La preuve PDF utilise seulement les deux dernières valeurs qui lui sont nécessaires (`WIF_PROVIDER`, `SOURCE_READER_SA`) ; le déploiement contrôle les trois variables historiques avant de prendre l'identité du déployeur.

**Ce que le déploiement automatique ne fait pas** (NFR13, et c'est écrit plutôt que sous-entendu) : ni Cloud Armor, ni load balancer, ni domaine personnalisé, ni SLO, ni supervision, ni test de charge, ni évals en intégration continue (le sous-ensemble rapide vient en 4.1). Le limiteur reste best-effort par instance.

## `data/` — pourquoi des liens symboliques pendants dès le clone

`data/` n'est pas un répertoire ordinaire : c'est la **projection d'un espace de publication A/B**
(`server/evals/espace.py`, `server/app/corpus/racine.py`). Chaque artefact et chaque source y est un
lien vers `data/.publie/courant/…`, et le pointeur `courant` bascule d'une génération à l'autre en
une seule opération — c'est ce qui rend une ingestion ou un run d'évals tout-ou-rien.

**Un lien pendant y est un état voulu, pas une casse.** La disposition déclare pour *chaque*
document les six artefacts et les quatre sources possibles ; celles qui n'existent pas pour ce
document-là restent des liens sans cible, et le code les lit comme telles — `racine.py` :
`except FileNotFoundError: continue  # lien pendant exact : absence métier publiée`. C'est délibéré,
et c'est aussi ce qui **interdit** de les supprimer : le même code refuse de publier
(`EspaceNonInstalle`) dès qu'un des dix noms manque pour un document.

Sur un clone, treize liens sont donc pendants, et chacun dit une absence exacte :

| Lien pendant | Ce qu'il dit |
|---|---|
| `data/lux-guide/source.pdf` | le guide vient d'un `source.js`, il n'a pas de PDF |
| `data/{axa,baloise}/source.js` | les contrats viennent d'un PDF, ils n'ont pas de source JS |
| `data/lux-guide/{source.sha256,dictionary.json,typing.manual.json,structure.json}` | sans objet pour un guide, ou pas encore publié dans cette image |
| `data/{axa,baloise}/{typing.manual.json,structure.json}` | aucun typage manuel ni proposition de structure publiés dans cette image |
| `data/evals-latest.json` | aucun run d'évals publié dans cette image — `/api/v1/evals/latest` répond `{"publie": false, "raison": "absent"}`, et l'accueil l'affiche comme une absence, pas comme un trou |
| `docs/evals/campagnes` | aucune archive de campagne publiée dans cette image |

**Les deux PDF des contrats ne sont pas committés** (droits de diffusion) : `fetch_source` les
télécharge au build, empreinte vérifiée contre `data/<doc>/source.sha256`, avec repli sur
`gs://foyer-retour-sources/`.

## Principes

- **Restitution d'abord** : source par affirmation, état explicite (sûr / partiel / inconnu), trace consultable par réponse, coût affiché.
- **Déterminisme sur les vrais invariants** : le modèle propose, le code vérifie ; pas de verdict sans clause citée et retrouvée mot pour mot dans la source.
- **L'intelligence se paie une fois, à l'ingestion** ; la requête reste légère.
- **Un document mal ingéré n'est pas servi** : rapport d'ingestion visible, quarantaine.
- **Écrit pour être relu** : petits commits qui disent pourquoi, README pour le mainteneur qui arrive.
